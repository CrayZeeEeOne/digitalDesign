# DSP у залізі (`dsp_top`)

Уся обробка сигналу, яку раніше робив MicroBlaze (колишній `vitis/src/dsp/`), тепер іде в PL.
Прошивка лише налаштовує блок, чекає на захоплення, забирає його через AXI і малює
екрани. C-код DSP перенесено в `tools/host_sim/model/` (`dsp/`, `source/`) як еталонну модель
для host-симулятора; у `vitis/src` лишився тільки код плати.

```
 MicroBlaze --AXI4-Lite--> iq_stream_top (0x44A3_0000)  FIFO I/Q, 1024 слова
                               | M_AXIS (replay файлу з SD -- коли буде робоча картка)
                               v
 MicroBlaze --AXI4-Lite--> dsp_top (0x44A4_0000, 16 КБ)
                               |
            +------------------+---------------------------+
            | SRC_CTRL: S_AXIS або iq_gen                  |
            v                                              |
   iq_gen: GFSK-пакети в шумі (формат sim.iq)             |
            |                                              |
            +--> rtl_demod: NCO -> CIC/16 -> CORDIC -> burst -> слайсер, такт ->
            |               sync 0x91D3 -> байти -> CRC-16  (результат + 48 байт)
            +--> dsp_capture: 384 колонки min/max I/Q, біти 2 пакетів
            +--> dsp_spectrum: Ханн -> FFT-256 -> |re|+|im| -> 40 рядків waterfall
```

Один відлік потоку бачать усі три блоки одночасно. Відлік приймається, коли
демодулятор увімкнений і FFT має вільний банк, тож при швидкому replay потік
просто пригальмовує.

## Файли

| Файл | Що робить |
|---|---|
| `rtl/dsp_top.v` | Verilog-обгортка для Block Design (порти S_AXI, S_AXIS) |
| `rtl/dsp_regs.sv` | AXI4-Lite, мапа регістрів, вибір джерела, з'єднання блоків |
| `rtl/iq_gen.sv` | тестове джерело: кадр `AA x8, 91D3, "DF5 PKTnn ", дані, CRC`, BT 0.5, шум |
| `rtl/rtl_demod_bank.sv` | регістри + пам'ять пакета демодулятора (той самий банк у `rtl_demod_regs`) |
| `rtl/rtl_demod.sv` ... `demod_*.sv` | ядро демодулятора (без змін, крім відводів `tap_*`) |
| `rtl/dsp_capture.sv` | стан захоплення, колонки I/Q, біти пакетів |
| `rtl/dsp_spectrum.sv` | вікно, FFT-256, накопичення, рядки waterfall |
| `mem/fft_hann256.mem`, `fft_tw128.mem` | вікно Ханна і готові twiddle `{wi, wr}` -- пораховані тим самим кодом, що `fft.c` |
| `mem/gen_gauss.mem` | гауссів імпульс GFSK для `iq_gen` (3 x 256) |
| `vitis/src/hal/dsp_rtl.c` | драйвер: конфігурація з `config.h`, старт, опитування, читання |

Таблиці генерує `tools/gen_mem.py`.

## Мапа регістрів `dsp_top`

Повна мапа — у шапці `dsp_regs.sv`. Коротко:

| Адреса | Що |
|---|---|
| `0x0000..0x01FF` | демодулятор, мапа `rtl_demod_regs` (CTRL, NCO_INC, DECIM, BIT_INC, SYNC_WORD, PKT_LEN, результат, пам'ять пакета) |
| `0x0200` | `SRC_CTRL`: [0] 1 = генератор, [1] генератор увімкнено |
| `0x0204..0x021C` | генератор: темп, зсув несучої, девіація, бітрейт, амплітуда/шум, період, пауза |
| `0x0300` | `CAP_CTRL`: [0] arm, [1] abort |
| `0x0304` | `CAP_STATUS`: стан (0 idle, 1 warmup, 2 wait, 3 record, 4 done), пакетів, рядків |
| `0x0308..0x0314` | warmup, довжина, колонки (len/384, len%384), режим (shift рядка, без очікування) |
| `0x0318`, `0x031C` | позиція запису, номер першого записаного відліку потоку |
| `0x0320 + 16p` | пакет p: START, END, FIRST_BIT, NBITS |
| `0x0400` | біти пакетів, по 64 байти (MSB першим) |
| `0x0800` | 384 колонки `{q_hi, q_lo, i_hi, i_lo}` (int8) |
| `0x2000` | waterfall 40 x 128 байт |
| `0x02FC` | ID `0x4453_5001` |

Max hold спектра прошивка рахує сама з рядків waterfall.

## Захоплення

Як у колишньому `capture.c`: `arm` → `WARMUP` (16384 відліки, оцінювачі шуму й
AFC встигають усталитися) → `WAIT` (до кінця пакета, щоб запис почався в паузі;
режим `CAP_MODE[8]` пропускає це очікування для файлу, записаного з початку) →
`RECORD` (327680 відліків = 72.8 мс, два періоди пакета) → `DONE`.

FFT обробляє лише блоки по 256 відліків, у яких хоч один відлік записувався.
32 блоки дають один рядок waterfall, разом 40 рядків.

## Перевірка

```
scripts\sim_tb.bat tb_dsp_top      xsim без проєкту; після TB -- tools\check_dsp_capture.py
scripts\sim_tb.bat tb_rtl_demod    демодулятор на sim.iq + траса Python-моделі
```

`tb_dsp_top`:
- **T1** — ID і значення після скиду.
- **T2** — генератор → демодулятор: 3 пакети, байти й CRC збігаються з очікуваними.
- **T4** — генератор + захоплення з очікуванням пакета: 2 пакети по ~468 біт.
- **T3** (після T4, як на платі: файл після захоплення з генератора) — `sim.iq` через
  S_AXIS: 2 пакети з CRC OK; захоплення доходить до DONE, дамп колонок і waterfall
  звіряє `check_dsp_capture.py` з C-алгоритмом **біт у біт**, а біти пакетів — із
  кадрами з `sim.iq.json` (0 помилок).

На платі те саме перевіряється дампом через JTAG: replay `SIM.IQ` з SD →
`check_dsp_capture.py` на дампі (див. нижче).

## Пастки синтезу, на які вже наступили

RTL-симуляція проходила, а на платі спектр був неправильний. Знайдено порівнянням
RTL із post-synthesis netlist (`write_verilog -mode funcsim`) такт за тактом:

* **Таблиця на 257 слів** (`sin[0..256]`): Vivado будує ROM на 256 слів, і адреса 256
  загортається в 0. Симулятор читає правильно.
* **Дві копії однієї ROM через функцію** (`sin_q15(ph + 90)` і `sin_q15(ph)` в одному
  блоці): у netlist одна з копій давала 0 для будь-якої адреси з таблиці.

Тепер twiddle не рахуються в RTL: `tools/gen_mem.py` рахує їх тим самим кодом, що й
`fft.c`, і кладе в одну ROM `fft_tw128.mem` (128 x `{wi, wr}`), RTL лише читає слово
за індексом `m = k << (7 - стадія)`. Висновок для нових блоків: ROM -- лише
степінь двійки слів, одна точка читання, жодної арифметики індексу у функціях.

Ще одна знахідка на платі: якщо `arm` приходить, поки FFT добирає блоки
попереднього захоплення, вони потрапляли в перший рядок нового. Тепер `arm`
обриває FFT і відкидає блок, що чекає.
