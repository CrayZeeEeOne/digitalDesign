# DF5: як працює все, від RTL до пікселя

Цей документ пояснює весь робочий код проєкту так, щоб для розуміння не треба
було відкривати джерела: кожен RTL-модуль, кожен C-файл, і всередині них --
кожен блок коду (always-блок, стадію конвеєра, функцію). Числа наведено для
конфігурації, з якою прошивка реально працює (`vitis/src/config.h`).

Порядок: спочатку загальна картина і числа, потім залізо (RTL) блок за блоком,
потім прошивка шар за шаром, потім "що відбувається в часі" і як усе
перевіряється.

## 1. Загальна картина

Плата PA35T-StarLite (FPGA Artix-7 xc7a35t). У FPGA зібрано процесор
MicroBlaze і кілька власних блоків. Зовні до плати під'єднані дисплей ST7789
(320x240, SPI), дві кнопки, два світлодіоди і microSD-карта.

Задача: прийняти I/Q-сигнал з пакетами 2-FSK/GFSK, демодулювати його
(знайти пакети, витягти біти, перевірити CRC) і показати чотири екрани:
сирий сигнал, біти, спектр (FFT) і waterfall.

**Поділ роботи:** уся обробка сигналу виконується в залізі (PL). MicroBlaze
лише налаштовує регістри, забирає результати і малює.

```
                         ┌─────────────────────── dsp_top (0x44A40000) ───────────────────────┐
                         │                                                                    │
 microSD ─ AXI Quad SPI ─┤                                                                    │
     │   (0x44A20000)    │   iq_gen ──┐                         ┌─> rtl_demod  ─> пакети, CRC │
     ▼                   │  (генератор│   src_sel   один і той  │                             │
 MicroBlaze ─ FatFs ─────┼─> iq_stream├──> мультиплексор ──────┼─> dsp_spectrum ─> waterfall │
     │   (replay SIM.IQ) │  (FIFO,    │   джерела    самий       │                  (кільце)   │
     │                   │ 0x44A30000)┘              відлік      └─> dsp_capture ─> колонки,   │
     │                   │                                                         біти       │
     │                   └────────────────────────────────────────────────────────────────────┘
     │
     ├─ AXI4-Lite ─> tft_top (0x00010000) ─ SPI 25 МГц ─> дисплей ST7789
     └─ AXI4-Lite ─> system_ctrl_top (0x44A10000) ─ кнопки, LED, лічильник часу
```

Джерел сигналу два:

- **Генератор `iq_gen` у залізі.** Він видає GFSK-пакети в шумі в реальному
  часі (4.5 млн відліків/с). Це основний, "живий" режим.
- **Файл `SIM.IQ` з SD-карти.** MicroBlaze читає файл через FatFs і штовхає
  відліки в FIFO `iq_stream`, звідти вони йдуть у той самий DSP. Картка
  читається повільніше за реальний час, але алгоритм рахує "на відлік", а не
  "на секунду", тому результат той самий.

Кожен прийнятий відлік одночасно бачать усі три споживачі: демодулятор,
спектр і захоплення.

## 2. Сигнал, формати чисел, ключові числа

### 2.1 Що таке I/Q-відлік

Відлік -- це комплексне число `I + jQ`: дві 16-бітні знакові цілі
(-32768..32767). На шині вони пакуються в одне 32-бітне слово:
`[15:0] = I`, `[31:16] = Q`. Файл `SIM.IQ` має той самий формат:
int16 I, int16 Q, little-endian, по черзі.

Частота 0 Гц у I/Q відповідає несучій приймача (LO) 867.4 МГц. Від'ємні
частоти лежать нижче LO, додатні -- вище.

### 2.2 Параметри сигналу (config.h)

| Що | Значення | Звідки число |
|---|---|---|
| Частота дискретизації Fs | 4.5 МВід/с | `CFG_SAMPLE_RATE_HZ` |
| Такт FPGA (AXI) | 100 МГц | `CFG_ACLK_HZ`; на один відлік ~22 такти |
| LO | 867.4 МГц | `CFG_CENTER_FREQ_HZ` |
| Канал | 866.31 МГц, тобто -1.09 МГц від LO | `CFG_CHANNEL_FREQ_HZ` |
| Похибка несучої генератора | +3 кГц | `GEN_CFO_HZ` у dsp_rtl.c |
| Бітова швидкість | 19200 біт/с | 234.375 відліків на біт |
| Девіація | 25 кГц | `CFG_DEVIATION_HZ` |
| Формат кадру | 8 x 0xAA, sync 0x91D3, 46 байт, CRC-16 | разом 58 байт = 464 біти |
| Тривалість пакета | 24.17 мс = 108750 відліків | |
| Період пакетів генератора | 156250 відліків = 34.7 мс | з них 47500 (10.6 мс) -- лише шум |
| Захоплення | 327680 відліків = 72.8 мс | вміщує 2 пакети |

### 2.3 Фіксована кома: як читати числа в коді

- **Фаза NCO** -- 32-бітне беззнакове, повний оберт (2π) = 2^32. Крок
  `inc = f / Fs * 2^32`. Переповнення лічильника -- це і є загортання фази.
- **Кут / миттєва частота `dphi`** -- 16-бітне знакове, де 2^15 = π рад.
  Наприклад, при Fs_dec = 281.25 кГц девіація 25 кГц -- це
  `2π * 25/281.25 рад = 0.559 рад`, тобто ~5825 у цих одиницях.
- **Q15** -- знакове 16-бітне з 15 дробовими бітами: 32767 ≈ 1.0. Так
  записані синуси, вікно Ханна, twiddle-коефіцієнти FFT і гауссів імпульс.
- **Рівень спектра** -- байт `≈ 16 * log2(|X|)`: 16 кроків на подвоєння
  амплітуди, тобто 0.376 дБ на крок. 0 дБFS = 224.

### 2.4 Частотна сітка спектра

FFT-256 при Fs = 4.5 МГц дає крок 17.58 кГц на бін. Показується 128 бінів,
тобто 2.25 МГц. Вікно центроване на каналі:

- `SPEC_CH_BINS` = -62 -- скільки бінів канал від LO;
- `SPEC_BIN0 = (-62 - 64) & 255` = 130 -- перший бін вікна.

Виходить вікно 865.19 ... 867.44 МГц, канал якраз посередині (бін 64 зі 128).

## 4. RTL

Усі джерела лежать у `vivado/sources/rtl/`. Усі блоки працюють на одному
такті 100 МГц і мають синхронний скид. Кожен блок, видимий у Block Design,
має тонку Verilog-2001 обгортку (`*_top.v`): IP Integrator вміє розпізнати
AXI-інтерфейс лише за плоскими портами з іменами за конвенцією Xilinx.
Логіки в обгортках немає.

Ієрархія того, що реально працює на платі:

```
dsp_top.v
└── dsp_regs.sv
    ├── axi_lite_regs.sv
    ├── iq_gen.sv
    ├── rtl_demod_bank.sv
    │   └── rtl_demod.sv
    │       ├── demod_nco_mixer.sv
    │       ├── demod_cic3.sv
    │       ├── demod_discriminator.sv
    │       │   └── demod_cordic_atan2.sv
    │       ├── demod_power.sv
    │       └── demod_bit_decoder.sv
    ├── dsp_capture.sv
    └── dsp_spectrum.sv
iq_stream_top.v ── iq_stream_regs.sv ── axi_lite_regs.sv, iq_stream_fifo.sv
tft_top.v ── spi_tft_ctrl.sv
system_ctrl_top.v ── system_ctrl_regs.sv ── axi_lite_regs.sv
```

### 4.1 `axi_lite_regs` -- міст AXI4-Lite

**Навіщо.** AXI4-Lite має п'ять каналів із рукостисканнями (AW, W, B, AR,
R). Цей модуль реалізує протокол один раз і перетворює його на просту шину
"запиши слово / прочитай слово". Ним користуються `dsp_regs`,
`iq_stream_regs` і `system_ctrl_regs`.

**Блок запису.**

- Адреса (AW) і дані (W) можуть прийти в будь-якому порядку і в різних
  тактах. Прапори `aw_done` / `w_done` пам'ятають, що канал уже прийнятий, а
  `aw_q` / `w_q` / `strb_q` -- його значення.
- `wr_en` -- рівно один такт, коли є обидві половини. Якщо половина приходить
  у цьому ж такті, її значення береться прямо з шини, тому зайвого такту
  немає.
- Після `wr_en` піднімається `bvalid` (відповідь OKAY). Поки майстер її не
  забрав, `awready` / `wready` тримаються в 0, тож нова транзакція не почнеться.

**Блок читання.**

- Такт 0: адресу прийнято (`ar_hs`). Вона защіпується в `rd_addr`, а в цьому
  ж такті одноразовим імпульсом виходить `rd_req` з `rd_req_addr`.
- Такт 1: `rd_en` (= `rd_pending`). Значення `rd_data`, яке користувач видав
  комбінаційно за `rd_addr`, защіпується в `s_axi_rdata`, піднімається `rvalid`.

Навіщо `rd_req` на такт раніше: блокова пам'ять (BRAM) віддає дані з
затримкою в один такт. Користувач подає адресу в BRAM по `rd_req`, і до такту
`rd_en` дані вже готові. Так читаються колонки, біти і waterfall у
`dsp_regs`.

Усі відповіді OKAY. Адреса поза мапою читається як 0, це вирішує
користувач.

### 4.2 `dsp_top` / `dsp_regs` -- весь DSP за однією адресою

`dsp_top.v` -- обгортка без логіки: порти S_AXI (адреса 16 біт, тобто 64 КБ),
S_AXIS (вхідний потік I/Q від `iq_stream`) і `irq`. Уся логіка -- у
`dsp_regs.sv`, який складається з таких частин.

**Міст AXI.** Екземпляр `axi_lite_regs` з шириною адреси 16 біт. Запис іде
у два місця:

- `wr_demod` -- адреси 0x000..0x1FF йдуть у банк демодулятора;
- `wr_ctl` -- адреси 0x200..0x3FF йдуть у регістри цього модуля.

**Регістри керування (always-блок зі скидом).** Після скиду в них лежать
робочі значення, тому блок працює навіть без налаштування з софту:
генератор на -1087 кГц, 4.5 МВід/с, амплітуда 6000, шум 1470; захоплення
16384 + 327680 відліків; BIN0 = 192 (центр FFT). `cap_arm` і `cap_abort` --
одноразові імпульси: стоять в 1 рівно один такт після запису. Регістри:

| Адреса | Назва | Поле |
|---|---|---|
| 0x200 | SRC_CTRL | [0] джерело (0 = S_AXIS, 1 = генератор), [1] генератор увімкнено |
| 0x204..0x21C | GEN_* | темп, зсув несучої, девіація, бітовий крок, рівні, період, пауза |
| 0x300 | CAP_CTRL | [0] arm, [1] abort |
| 0x308 / 0x30C | CAP_WARMUP / CAP_LEN | відліки розгону / запису |
| 0x310 | CAP_COL | len/384 і len%384 -- для меж колонок без ділення в залізі |
| 0x314 | CAP_MODE | [4:0] log2(блоків FFT на рядок), [8] не чекати кінця пакета |
| 0x340 | SPEC_CTRL | [0] live-спектр |
| 0x348 | SPEC_BIN0 | перший бін вікна |

**Джерело і рукостискання потоку.** Це найважливіше місце модуля:

```
src_valid  = src_sel ? gen_valid : s_axis_tvalid
sink_ready = spec_ready && demod_en
fire       = src_valid && sink_ready      -- відлік прийнято
```

- Відлік приймається лише тоді, коли демодулятор увімкнений (`CTRL.enable`)
  і спектр має вільний банк (`spec_ready`).
- У такті `fire` той самий `src_data` бачать усі три споживачі:
  - демодулятор -- через свій `s_axis_tvalid = src_valid && spec_ready`;
  - захоплення -- через `in_fire = fire`;
  - спектр -- через `in_valid = fire`.

  Тому жоден із них не може "з'їсти" відлік, якого не побачили інші.
- `ready` повертається лише вибраному джерелу: `gen_ready = src_sel &&
  sink_ready`, `s_axis_tready = !src_sel && sink_ready`.
- Генератор, якому не дали `ready`, просто чекає (див. 4.3).

**Екземпляри.**

- `iq_gen u_gen` -- генератор, з конфігурацією з регістрів.
- `rtl_demod_bank u_demod` -- демодулятор. Назовні виходять його `tap_*`
  (події пакета, бітові рішення) для захоплення, `irq` і `st_enable`.
- `dsp_capture u_cap` -- захоплення. Читання через `rd_req` / `rd_req_addr`
  (синхронна пам'ять): колонки за адресою [10:2], біти -- за [6:2].
- `dsp_spectrum u_spec`. Його `arm = cap_arm && !spec_live`: у live-режимі
  перезапуск захоплення не чіпає спектр, кільце рядків іде безперервно.

**Мультиплексор читання.** Два always_comb:

1. `ctl_rd` -- регістри 0x200..0x3FF.
   - CAP_STATUS (0x304) збирається з полів: стан, done, кількість пакетів,
     "пакет пишеться", FFT зайнятий, рядки waterfall (обрізано до 255).
   - Позиції пакетів (0x320 + 16*p): START, END, FIRST_BIT, NBITS.
2. `rd_data` за старшими бітами адреси:

   | Адреса | Звідки |
   |---|---|
   | 0x0000 | демодулятор |
   | 0x0200 | `ctl_rd` |
   | 0x0400 | біти пакетів |
   | 0x0800 | колонки |
   | 0x8000.. (біт 15) | waterfall |

`unused_ok` -- це просто згортка невикористаних сигналів, щоб синтез не
сварився.

### 4.3 `iq_gen` -- тестовий GFSK-генератор

**Що робить.** Видає I/Q того самого формату, що й `sim.iq`
(tools/iqgen.py). У кожному періоді (`cfg_period` = 156250 відліків):

- спочатку `cfg_gap` = 47500 відліків чистого шуму;
- потім пакет із 464 біт GFSK-модуляцією, поверх шуму.

**Темп відліків (always-блок `rate_acc`).** 32-бітний акумулятор щотакту
додає `cfg_rate = 2^32 * 4.5 / 100`. Перенос (`s[32]`) означає "настав час
наступного відліку" і ставить `pending`. FSM забирає його сигналом `take`.
Так виходить рівно 4.5 МВід/с з такту 100 МГц без дільника. Якщо споживач не
готовий (`out_ready = 0`), `out_valid` тримається, нові відліки не
рахуються, і темп просто падає. Нічого не губиться.

**Байти кадру (функції `frame_byte`, `tag_char`).** Байт `i` кадру
обчислюється комбінаційно, без пам'яті:

| Байти | Вміст |
|---|---|
| 0..7 | 0xAA (преамбула) |
| 8..9 | 0x91, 0xD3 (sync) |
| 10..19 | текст `"DF5 PKTnn "`, де nn -- десятковий номер пакета (лічильники `tens` / `ones`) |
| 20..55 | `17*k + 7*m + 0x42`, де k -- номер пакета, m -- номер байта від 10 |
| 56..57 | CRC-16/CCITT-FALSE (поліном 0x1021, старт 0xFFFF) |

CRC рахується по ходу передачі біт за бітом (по бітах 80..447, тобто по 46
байтах payload). До моменту, коли треба передати байти 56..57, CRC уже готовий.

**Біти наперед.** Згладжування Гаусом бере три біти: попередній, поточний і
наступний. Тому FSM тримає пари (`b_prev`, `v_prev`), (`b_cur`, `v_cur`),
(`b_next`, `v_next`): значення біта і прапор "біт існує" (поза кадром біт
вважається відсутнім). `gen_n` -- номер біта, що буде наступним, з нього
`gb_bit = frame_byte(gen_n/8)[7 - gen_n%8]`.

**FSM: один відлік за 8 тактів.** Між відліками ~22 такти, тож запас
великий.

1. **S_IDLE.** Чекає `pending`. Якщо лічильник періоду `scnt == cfg_gap` --
   починається пакет: `burst = 1`, бітова фаза 0, поточний біт -- перший біт
   0xAA (=1), наступний -- 0, CRC = 0xFFFF.
2. **S_G0, S_G1, S_G2, S_FREQ -- гауссове згладження NRZ.** Таблиця
   `gauss[0:767]` -- це три відрізки по 256 точок: внесок наступного,
   поточного і попереднього біта залежно від положення всередині біта (`ph8 =
   bit_ph[31:24]`). Кожен внесок додається зі знаком біта (1 -> +, 0 -> -), якщо
   біт існує. Результат `shp` -- згладжений NRZ у Q15. У S_FREQ рахується
   `dev_prod = cfg_dev * shp`, а `dev_shf = dev_prod >>> 15` -- приріст фази
   від модуляції.
3. **S_PHASE.**
   - Фаза несучої: `phase += cfg_fofs + (burst ? dev_shf : 0)`. Поза пакетом
     несучої немає, але фаза все одно крутиться -- це не має значення.
   - Чотири генератори xorshift32 роблять крок.
4. **S_LUT.**
   - `sin` і `cos` з таблиці 1024 точок: `cos = sin[idx + 256]`.
   - Шум I і Q -- сума чотирьох 12-бітних рівномірних чисел. За центральною
     граничною теоремою це майже гаусів шум.
5. **S_MUL.**
   - Сигнал: `amp * cos >> 15`, `amp * sin >> 15`; поза пакетом -- нуль.
   - Шум множиться на `cfg_noise`.
6. **S_OUT.**
   - Відлік = сигнал + шум >> 13, з насиченням до 16 біт. Піднімається
     `out_valid`.
   - Під час пакета бітова фаза `bit_ph += cfg_bit_inc`. Перенос означає
     наступний біт: трійка бітів зсувається, береться новий `b_next`, CRC
     оновлюється, якщо біт у payload.
   - Після 464-го біта `burst = 0`, `st_pkts++`, номер пакета для тексту +1
     (00..99).
   - `scnt` рахує позицію в періоді за модулем `cfg_period`.

Підсумок: рівень шуму 1470 дає СКВ ≈ 424 LSB, амплітуда 6000 -- SNR ≈ 20 дБ,
як у `sim.iq`.

### 4.4 `rtl_demod_bank` -- регістри демодулятора

Обгортка навколо ядра `rtl_demod` у вигляді банку регістрів 512 байт.
Займає 0x000..0x1FF у `dsp_top`.

**Регістри конфігурації (always-блок зі скидом).** Після скиду в них уже
готова конфігурація задачі. Софт однаково переписує їх із config.h.

| Адреса | Регістр | Значення / смисл |
|---|---|---|
| 0x000 | CTRL | [0] enable; [1] soft_reset, [2] clr_stats, [3] ack_result -- одноразові імпульси |
| 0x008 | NCO_INC | 0x3E02468B = +1.09 МГц / 4.5 МГц * 2^32: зсуває канал у 0 Гц |
| 0x00C | DECIM | R = 16, зсув CIC = 12 (= 3*log2 16) |
| 0x010 | BURST_THR | 0 = поріг автоматично, 8 x шум |
| 0x014 | BIT_INC | 4474 = 19200 * 16 / 4.5 МГц * 65536 |
| 0x018, 0x01C | SYNC_WORD, PKT_LEN | 0x91D3, 48 байт після sync (з CRC) |
| 0x020, 0x024 | CRC | поліном 0x1021, старт 0xFFFF, очікуваний залишок 0 |
| 0x028, 0x02C | FREQ_INIT, AFC_CFG | старт порогу слайсера; зсуви IIR 4 / 7, девіація 5, "швидка фаза" 128 відліків |

**Лічильники.** Чотири 32-бітні лічильники: пакетів (burst), прийнятих
кадрів, кадрів із CRC OK і з CRC ERROR. Обнуляються скидом або `clr_stats`.
Рахують за подією `ev_burst_start` і за `res_strobe` з `res_kind == 0`.

**Защіпка результату.** На кожен `res_strobe` ядра всі вимірювання
копіюються в регістри `r_*`: прапори, довжина / потужність / пік пакета,
шум, поріг слайсера і девіація, вікно вимірювання, кількість байтів. Потім
піднімається `result_valid`; він же виходить як `irq`. Якщо попередній
результат ще не забрали, ставиться `result_overrun`. Софт знімає прапор
записом `ack_result`.

Поля `RES_FLAGS` (0x060):

| Біти | Поле |
|---|---|
| [0] | burst, завжди 1 |
| [1] | преамбула знайдена |
| [2] | sync знайдено |
| [3] | CRC OK |
| [4] | біти інвертовані |
| [5] | пакет обірвався |
| [7:6] | `kind`: 0 = пакет, 1 = burst без sync, 2 = обірваний |
| [15:8] | пакетів у цьому burst |
| [31:16] | бітів прийнято |

**Пам'ять пакета.** Чотири масиви по 64 байти (`pkt_mem0..3`), по одному на
байтову позицію в слові. Тому слово з чотирьох байтів читається за один
такт, а кожен масив має один порт запису і лягає в LUTRAM, а не в тригери.
Байт `n` пакета лежить у `pkt_mem[n%4][n/4]`. Для AXI це адреси
0x100..0x1FF, перший байт -- у бітах [7:0] слова 0x100.

**Читання.** Комбінаційний `case` за адресою: регістри конфігурації,
живий стан (шум, `pavg`, поріг, лічильники відліків), лічильники, защіпнутий
результат, ID 0x44534D01.

### 4.5 `rtl_demod` -- ланцюг демодулятора

Тут немає власної логіки: модуль з'єднує стадії і рахує вхідні та
децимовані відліки (`st_in_count`, `st_dec_count`). Ланцюг:

```
s_data ─> demod_nco_mixer ─> demod_cic3 (/16) ─> demod_discriminator ─> demod_power ─> demod_bit_decoder
 4.5 МВід/с                     281.25 кВід/с     dphi (кут між          burst,           біти, sync,
                                                  сусідніми відліками)   поріг, шум       байти, CRC
```

`s_ready = cfg_enable`: поки демодулятор вимкнений, потік стоїть, і
`dsp_regs` не приймає відліків узагалі. Завдяки цьому софт встигає все
налаштувати до того, як піде сигнал.

Відводи `tap_*` -- це вихід `demod_power` (кожен децимований відлік, прапори
burst / start / end) і бітові рішення `demod_bit_decoder`. Їх використовує
`dsp_capture`.

### 4.6 `demod_nco_mixer` -- перенесення каналу в 0 Гц

Множить вхідний відлік на `e^{+jθ}`, де θ росте на `nco_inc` за відлік.
Канал на -1.09 МГц переїжджає в 0 Гц; від генератора лишається тільки його
+3 кГц похибки.

- **Фаза.** Always-блок `phase += nco_inc` на кожен прийнятий відлік.
  Індекс у таблицю -- старші 10 біт фази. `sin = lut[idx]`, `cos =
  lut[idx + 256]` (чверть періоду).
- **Стадія 1.** Защіпка I, Q, sin, cos.
- **Стадія 2.** Чотири добутки `I*cos`, `Q*sin`, `I*sin`, `Q*cos`; кожен
  лягає в DSP48.
- **Стадія 3.**
  - `I' = I*cos - Q*sin`, `Q' = I*sin + Q*cos` -- комплексне множення.
  - Беруться біти [31:16], тобто результат ділиться на 2^16. Таблиця Q15,
    тому сумарне підсилення 1/2 -- сума двох добутків гарантовано влазить у
    16 біт без насичення.

Латентність 3 такти; `valid` іде поруч із даними.

### 4.7 `demod_cic3` -- децимація в 16 разів

CIC-фільтр 3-го порядку: три інтегратори на вхідній швидкості, три
гребінці на вихідній. Він одночасно фільтрує (прибирає все, що далі ~±140
кГц від каналу) і зменшує темп у R = 16 разів: з 4.5 МВід/с до 281.25
кВід/с. Множень він не потребує взагалі.

- **Інтегратори** (always-блок 1). На кожен вхідний відлік `ii1 += I`, `ii2
  += ii1`, `ii3 += ii2`, так само для Q. Регістри 32-бітні і переповнюються
  -- для CIC це нормально, бо гребінці віднімають так само за модулем.
  Результат правильний, якщо `16 + 3*log2(R) <= 32`. Лічильник `cnt` на
  кожен R-тий відлік ставить `dec_strobe`.
- **Гребінці** (always-блок 2). Три послідовні різниці `di1 = ii3 - ic1`,
  `di2 = di1 - ic2`, `di3 = di2 - ic3` рахуються комбінаційно і
  защіпуються одним тактом на `dec_strobe`. `ic*` -- попередні значення.
  Вихід ділиться на підсилення R³ = 4096 зсувом `shift` = 12.
- **Насичення** (always-блок 3). До 16 біт.

### 4.8 `demod_discriminator` -- миттєва частота

FSK кодує біт частотою, тому треба знайти, на який кут повернувся вектор
між двома сусідніми відліками:

```
z[n] * conj(z[n-1]) = dot + j*cross
dot   = I*Ip + Q*Qp
cross = Q*Ip - I*Qp
dphi  = atan2(cross, dot)       (2^15 = π рад за відлік)
```

Знак `dphi` -- це, власне, біт (вище чи нижче несучої).

- **Стадія 1.** Добутки з попереднім відліком (`ip`, `qp`); попередній
  відлік оновлюється.
- **Стадія 2.** `dot` і `cross`, 34 біти.
- **Стадія 3.** Модуль більшого з `|dot|`, `|cross|` і кількість його
  провідних нулів (`clz34`). З них величина зсуву `sh3`: старший біт має
  стати бітом 32.
- **Стадія 4.** Обидва числа зсуваються на `sh3` вліво, беруться біти
  [33:16] (18 біт). Це нормалізація: кут не залежить від амплітуди, тому
  слабкий сигнал отримує ту саму точність, що й сильний.
- **CORDIC** (4.9). 16 ітерацій.

I і Q цього ж відліку проходять поруч через `aux` (32 біти). На виході вони
вирівняні з `dphi` -- потрібні для `demod_power`. Латентність 21 такт.

### 4.9 `demod_cordic_atan2` -- кут вектора

Конвеєрний CORDIC у режимі vectoring: вектор (x, y) повертають на відомі
кути `atan(2^-i)` так, щоб y дійшов до 0. Сума поворотів -- шуканий кут.
Множень немає, лише зсуви і додавання.

- **Стадія 0.** Якщо x < 0, вектор повертається на 180° (x, y змінюють
  знак), стартовий кут `z = π` (0x8000). Так вектор опиняється в правій
  півплощині, де CORDIC збігається.
- **Стадії 1..16** (generate). Якщо y >= 0, поворот за годинниковою
  стрілкою, `z += ATAN[i]`, інакше -- навпаки. Таблиця `ATAN` -- це
  `atan(2^-i)/π * 2^15`.
- **Нульовий вектор** (обидва нулі) дає кут 0 -- як у Python-моделі.
  Прапор `zero` йде конвеєром разом із даними.

Кут 16-бітний, тож загортання за 2π відбувається саме собою.

### 4.10 `demod_power` -- потужність, шум, детектор пакета

Визначає, де пакет, а де лише шум.

- **Стадія 1, 2.** `p = I² + Q²` -- миттєва потужність.
- **Стадія 3 -- IIR-фільтри і детектор.**
  - `pavg += (p - pavg) >> 4` -- швидке середнє (~16 відліків).
  - `noise += (pavg - noise) >> 8` -- повільне середнє, оновлюється лише
    поза пакетом. Перші 1024 відліки після скиду `noise` фільтрується з `>>
    4`, щоб швидко сісти на рівень. Після них ставиться `warmup_done`.
    Стартове значення шуму -- максимум, тож до прогріву пакет не детектується.
  - Поріг `thr_on`: якщо `BURST_THR != 0` -- він, інакше `8 * noise`
    (+9 дБ), але не менше 64.
  - Гістерезис: пакет починається, коли `pavg > thr_on`, і закінчується,
    коли `pavg < thr_on/2`. Так шум на межі не "дзвенить".
  - `burst_start` / `burst_end` -- однотактні прапори на першому відліку
    пакета і першому після нього.
  - Під час пакета рахуються його довжина (децимовані відліки), пік `pavg` і
    повільне середнє `burst_pwr` (`>> 6`).

`dphi` проходить конвеєром і виходить вирівняним з прапором burst.

### 4.11 `demod_bit_decoder` -- від частоти до байтів

Найскладніший модуль. На кожен децимований відлік усередині пакета робиться
все нижче. Арифметика побітово збігається з `tools/demod_model.py`.

**1. Слайсер з AFC.**

- Біт: `bit_now = (dphi > favg) ^ inverted`. Поріг `favg` -- середня
  частота пакета. У ній ховається похибка несучої (+3 кГц), тому поріг
  підлаштовується (AFC = automatic frequency control).
- `favg` -- IIR із 8 додатковими дробовими бітами:
  `favg += ((dphi << 8) - favg) >> sh`.
- Перші `cfg_fast_len` = 128 відліків пакета `sh = 4` (швидко), далі `sh = 7`
  (повільно, щоб біти не тягнули поріг).
- Після sync поріг заморожується: далі йдуть дані, а не чергування 1010, і
  середнє вже не є несучою.

**2. Девіація.** `dev += (|dphi - favg| << 8 - dev) >> 5` -- середнє
відхилення частоти від порогу. Теж заморожується після sync. Йде тільки у
вимірювання.

**3. Відновлення бітового такту.**

- 16-бітний NCO `bit_phase += bit_inc` (4474: 65536 / 14.65 відліків на біт).
  Перенос (`wrap`) -- момент рішення: біт береться саме тоді.
- Перехід рішення (`trans`, 0->1 або 1->0) має бути посередині між двома
  моментами рішення, тобто при фазі 0x8000. Помилка
  `ph_err = bit_phase - 0x8000`; на кожному переході фаза зсувається на
  `ph_err/4`. Так моменти рішення сідають на середину бітів.
- `ph_adj = ph_err >>> 2` винесено окремим знаковим сигналом. Усередині
  виразу з беззнаковим `bit_phase` оператор `>>>` став би логічним, і корекція
  для від'ємної помилки була б неправильною. На цьому вже горіли.

**4. Вікно вимірювання.** Поки останні 8 рішень чергуються (`alt8`: 0xAA або
0x55 -- це преамбула):

- від першого переходу рахуються відліки `win_cnt`, переходи `win_trans` і
  сума `dphi` (`win_fsum`);
- на кожному переході робиться знімок (`*_snap`);
- коли чергування закінчується, вікно заморожується.

Софт дістає з цього точний бітрейт `Fs_dec * trans / cnt` і несучу `fsum /
cnt` без пульсацій IIR.

**5. Преамбула і sync.**

- `hist` -- зсувний регістр останніх рішень. `h16 == 0xAAAA / 0x5555` -- є
  преамбула.
- `h16 == SYNC` -- sync знайдено. `h16 == ~SYNC` -- теж sync, але біти
  інвертовані (сигнал дзеркальний за частотою), тоді `inverted` перемикається
  і далі всі біти інвертуються.
- На sync: `synced = pkt_active = 1`, лічильники байтів і бітів = 0,
  `crc = cfg_crc_init`.

**6. Байти і CRC.**

- Після sync кожне рішення засувається в `byte_sh` (MSB першим) і в CRC
  (побітово: `crc = (crc << 1) ^ (crc[15] ^ bit ? poly : 0)`).
- Кожні 8 біт байт пишеться в пам'ять пакета (`pkt_we`, `pkt_waddr`,
  `pkt_wdata`).
- Після `pkt_len` = 48 байт: `res_strobe`, `res_kind = 0`, `res_crc_ok =
  (crc == residue)`. CRC пораховано по всіх байтах, включно з двома
  CRC-байтами, тому для правильного пакета залишок дорівнює 0.

**Початок і кінець пакета.**

- `in_burst_start` скидає весь стан (поріг = `cfg_freq_init`, вікно, sync,
  фаза).
- `in_burst_end`:
  - пакет ще приймався -> результат `kind = 2` (обірваний);
  - burst без жодного sync -> `kind = 1`.

**Відвід для захоплення.** `tap_bit_v` = момент рішення (`wrap`) усередині
пакета, `tap_bit` = рішення. Так `dsp_capture` записує всі біти слайсера від
початку burst, включно з преамбулою. Це те, що показує екран BITS.

**Поля результату.** Беруться з поточного стану комбінаційно. Строб --
регістр, тож у такті `res_strobe` значення ще старі, тобто правильні.

### 4.12 `dsp_capture` -- запис для екранів RAW і BITS

Одне захоплення -- це "фото" 327680 відліків (72.8 мс) у компактному
вигляді, без сирих відліків.

**Машина станів.**

| Стан | Що робить |
|---|---|
| IDLE | нічого |
| WARMUP | пропускає `cfg_warmup` відліків: демодулятор устигає оцінити шум |
| WAIT | чекає кінця пакета (`tap_end`), щоб запис почався в паузі між пакетами; не довше `cfg_len` відліків; при `cfg_nowait` цей стан пропускається |
| RECORD | `cfg_len` відліків |
| DONE | захоплення готове |

`arm` з будь-якого стану переводить у WARMUP і обнуляє все, `abort` -- в
IDLE. `st_t0` -- номер вхідного відліку (від скиду) на початку запису. `rec =
in_fire && RECORD` повідомляє спектру, що цей відлік записується.

**Колонки RAW.**

- Запис ділиться на 384 колонки. У кожній зберігається мінімум і максимум
  I та Q, у вигляді int8 з кроком 64 LSB (`raw_q`: `x >>> 6`, насичення
  ±127). Це обвідна сигналу, яку малює екран RAW.
- Межі колонок -- `c * len / 384` -- рахуються без ділення, кроками в дусі
  Брезенгема. `edge_pos` -- перший відлік наступної колонки; до нього щоразу
  додається `cfg_col_q` = 853, а залишок `edge_rem` накопичує `cfg_col_r` =
  128. Коли залишок >= 384, додається ще 1.
- Коли `pos` доходить до межі, колонка пишеться в `raw_mem[col]` словом
  `{q_hi, q_lo, i_hi, i_lo}`, і min/max починаються з поточного відліку.
- Остання колонка дописується окремо, в такті завершення запису.

**Пакети.** Щонайбільше 2 пакети.

- `tap_start` у RECORD: `pkt_start[p] = pos`, лічильник біт 0.
- Кожен `tap_bit_v`: біт засувається в `shreg`. Позиція першого біта
  пишеться в `pkt_first`. Кожні 8 біт байт іде в пам'ять (до 512 біт =
  64 байти на пакет).
- `tap_end`: `pkt_end[p] = pos`. Неповний останній байт вирівнюється вліво,
  щоб перший біт завжди був MSB.
- Якщо запис закінчився посеред пакета, він закривається так само.

Пам'ять бітів -- чотири байтові лани (як у 4.4), щоб слово читалося за
такт. Байт `k` пакета `p` -- за адресою `p*64 + k`.

Події демодулятора приходять із затримкою його конвеєра (кілька
децимованих відліків). Тому позиції пакетів трохи пізніші за моменти у
вхідному потоці. Для екрана це непомітно.

**Читання.** Синхронне (BRAM): `rd_en` = `rd_req` з мосту AXI.

### 4.13 `dsp_spectrum` -- FFT-256 і waterfall

Рахує спектр кожного (або лише записуваного) блоку з 256 відліків і складає
з них рядки waterfall. Арифметика побітово збігається з C-моделлю
(`tools/host_sim/model/dsp/fft.c`, `spectrum.c`); це перевіряє
`tools/check_dsp_capture.py`.

**Два режими.**

- **Захоплення** (`cfg_live = 0`).
  - Обробляються лише блоки, у яких хоч один відлік записувався (`in_rec`).
  - `arm` обнуляє рядки.
  - Пишуться рядки 0..39 по 32 блоки (8192 відліки = 1.82 мс на рядок); 40
    рядків = увесь запис.
- **Live** (`cfg_live = 1`).
  - Обробляється кожен блок потоку.
  - Рядок = 2^6 = 64 блоки = 16384 відліки = 3.64 мс; ~275 рядків за секунду.
  - Рядки пишуться в кільце з 256 штук без кінця. `st_rows` -- скільки
    всього записано; рядок N лежить у кільці на N % 256.

**Пам'ять.**

- Два банки 256 x 32 біти `{im, re}` (`bank0`, `bank1`) -- ping-pong: у
  один (`wb`) пише вхід, на другому (`fb`) працює FFT. Кожен банк -- BRAM з
  двома портами (A і B).
- Накопичувачі `acc[0:127]` -- 32-бітні суми рівнів бінів у рядку.
- Waterfall -- `WF_RING * 128` байт у чотирьох байтових ланах.

**Вхідна стадія (блок "вхід").**

- `n_in` -- номер відліку в блоці 0..255.
- Відлік множиться на вікно Ханна (`hann[n]`, Q15) і пишеться в банк `wb`
  за адресою `bitrev8(n)` -- у бітово-реверсному порядку. Тоді FFT
  "decimation in time" рахує на місці, і на виході біни йдуть у
  природному порядку.
- `blk_rec` пам'ятає, що в блоці був записуваний відлік або увімкнено live.
- На 256-му відліку блок або йде в обробку (`pend = 1`), або відкидається.
- Поки `pend = 1`, `in_ready = 0`, і весь потік у `dsp_regs` стоїть. Так
  відліки не губляться, якщо FFT ще не закінчив попередній блок.
- Коли FFT вільний, банки міняються місцями (`fb <= wb`, `wb <= ~wb`) і
  йде `fft_start`.
- `arm` відкидає блок, що чекає: блок старого захоплення не має потрапити в
  новий рядок.

**FFT, radix-2, 8 стадій по 128 метеликів.** Адреси метелика рахуються
комбінаційно зі `stage` і `bfly`:

```
half = 1 << stage       k = bfly & (half-1)      grp = bfly >> stage
ba   = (grp << (stage+1)) | k                    bb  = ba + half
twiddle m = k << (7 - stage)      (з ROM twrom[m] = {wi, wr}, Q15)
```

Конвеєр метелика: R -> M -> S -> W.

- **R (`phase_rd = 1`).** Адреси `ba`, `bb` на порти A і B банку `fb`.
  Twiddle з ROM.
- **M.** Дані з BRAM прийшли (латентність 1 такт). Чотири добутки
  `b * w`.
- **S.** `t = b*w >> 15`, `a' = (a + t) / 2`, `b' = (a - t) / 2`.
  Ділення на 2 на кожній стадії не дає числам вирости: за 8 стадій -- /256.
- **W.** Запис `a'` і `b'` на ті самі адреси.

Кожен порт банку і читає, і пише. Тому такти чергуються: читання -- на
парних (`phase_rd`), запис -- на непарних, і метелик займає 2 такти. Між
стадіями `F_DRAIN` чекає 5 тактів, поки останній запис стадії завершиться,
інакше наступна стадія прочитала б старі дані. Разом ~2100 тактів на блок
проти ~5700 тактів, за які в реальному часі приходять 256 відліків.

**Вихід (F_OUT, 128 тактів).**

- Читаються біни `k = (o_n + cfg_bin0) & 255` -- вікно 128 бінів навколо
  каналу (див. 2.4).
- Такт 1: `m = |re| + |im|` (наближення модуля без кореня), насичене до
  65535, плюс накопичене `acc[k]`.
- Такт 2: сума пишеться назад в `acc`. Якщо цей блок закінчує рядок
  (`row_last`: `blocks_lo == 2^shift - 1`), то:
  - у waterfall пишеться `spec_log(sum >> shift)` -- середній рівень бінів;
  - `acc` обнуляється.
- Рядок пишеться за адресою `{rows % 256, bin/4}`, у лан `bin % 4`. У
  режимі захоплення пишуться лише перші 40 рядків (`row_wr_ok`).

**`spec_log`.** `n` -- номер старшого одиничного біта, `fr` -- наступні 4
біти. `16*n + fr ≈ 16 * log2(x)`. Обрізається до 255.

**Обнулення накопичувачів.** Після скиду і після `arm` 128 тактів по одному
біну (`clr_act`). Також `arm` обриває FFT, що йде: його блок належить
старому захопленню.

**Читання з AXI.** Синхронне: слово з чотирьох лан = 4 сусідні біни, бін
`4w` -- у [7:0].

`st_busy` = FFT іде або блок чекає, або йде обнулення.

**Пастки синтезу, які тут уже обійшли.** Детально -- у
[`dsp_rtl.md`](dsp_rtl.md).

- ROM довжиною не степінь двійки (257) Vivado загорнув. Тому twiddle --
  окрема ROM рівно на 128 записів.
- Друге читання ROM через функцію синтезувалося в 0. Тепер читання пряме.

### 4.14 `iq_stream_regs` / `iq_stream_fifo` -- потік із SD

**FIFO** (`iq_stream_fifo`, 1024 x 32 біти, FWFT -- перше слово видно на
виході одразу).

- Пам'ять (BRAM) читається синхронно за `rd_ptr` у вихідний регістр
  `m_data`, щойно той вільний (`out_free`).
- Вказівники мають зайвий біт, щоб відрізняти "повний" від "порожнього".
- `level` = слова в пам'яті + вихідний регістр. `full` рахується за
  `level`, тому місткість рівно 1024 слова.
- Запис у повний FIFO ігнорується.

**Регістри** (`iq_stream_regs`).

| Адреса | Регістр | Смисл |
|---|---|---|
| 0x00 | CTRL | [0] enable -- без нього потік не виходить; [1] flush; [2] clr_stats |
| 0x04 | STATUS | empty, full, overflow, enable, рівень |
| 0x08 | DATA | запис -- одна пара I/Q у FIFO; читання -- слово на виході без вилучення |
| 0x0C..0x18 | LEVEL, PUSHED, POPPED, DROPPED | рівень і лічильники |
| 0x1C | ID | 0x49510001 |

Один запис DATA -- це завжди повна пара I/Q, тож половинка пари в DSP
потрапити не може.

**Вихід.** `m_axis_tvalid = fifo_valid && enable`, `tready` -- від `dsp_top`.

### 4.15 `spi_tft_ctrl` / `tft_top` -- SPI на дисплей

Простий байтовий SPI-майстер. Усю логіку дисплея (команди ST7789) знає
C-драйвер.

**Регістри.**

| Адреса | Регістр | Смисл |
|---|---|---|
| 0x00 | CTRL | [0] enable, [1] DC (0 = команда, 1 = дані), [2] RST дисплея, [3] CS вручну, [4] CS автоматично, [5] підсвітка |
| 0x04 | CLKDIV | `f_sclk = 100 МГц / (2*(div+1))`; div = 1 дає 25 МГц |
| 0x08 | TXDATA | запис кладе байт у FIFO |
| 0x0C | STATUS | busy, full, empty, рівень FIFO |
| 0x10 | ID | 0x5F778901 |

**TX FIFO** -- 16 байт, вказівники із зайвим бітом.

**SPI-машина** (режим 0, MSB першим).

- **IDLE.** Якщо є байт -- переходить у LOAD.
- **LOAD.** Байт з FIFO у `sh_tx`, 8 біт.
- **SHIFT.** `clk_cnt` відраховує півперіод (`tick`).
  - На фронті SCLK читається MISO.
  - На спаді виставляється наступний біт.
  - Після 8 біт -- одразу LOAD наступного байта, якщо FIFO не порожній.
    Тому байти йдуть без пауз.

**CS** в авторежимі активний, поки є що передавати.

**AXI.** Тут свій міст AXI4-Lite. Модуль написаний раніше за
`axi_lite_regs`, але логіка та сама.

### 4.16 `system_ctrl_regs` / `system_ctrl_top` -- кнопки, LED, таймер

**Антидребезг кнопок.**

- Входи (активні нулем, підтяжка) інвертуються і проходять синхронізатор з
  двох тригерів.
- Раз на мілісекунду (`ms_tick`) стан засувається в 8-бітну історію.
  Стабільний стан змінюється, лише коли всі 8 відліків однакові, тобто
  кнопка мусить простояти 8 мс.
- Фронти натискання і відпускання защіпуються в BTN_EVENT; знімаються
  записом 1 (W1C). Якщо новий фронт і скидання припадають на один такт,
  фронт перемагає.

**Регістри.**

| Адреса | Регістр |
|---|---|
| 0x00 | ID 0x53595301 |
| 0x04 | LED |
| 0x08 | BTN_RAW -- стабільний стан кнопок |
| 0x0C | BTN_EVENT |
| 0x18 | TICK -- вільний 32-бітний лічильник тактів 100 МГц; з нього софт рахує мілісекунди |
| 0x1C | SCRATCH |
| 0x20 | ACLK_HZ |
| 0x24 | сирі входи |

**Залишки.** Регістри SPI_CLKDIV і SD_CS, а також вихід `spi_clk` (дільник
такту з BUFG в обгортці) зараз ні до чого не під'єднані: SD-карта працює
через AXI Quad SPI, який сам керує CS і тактом.

## 5. Прошивка (MicroBlaze)

`vitis/src/`, збирається `scripts/build_elf.bat` у `vitis/elf/df5_app.elf`.
Без Vitis-платформи: компілятор `mb-gcc` з `-Os -flto`, власний старт і
скрипт лінкера.

Шари знизу вгору:

| Шар | Файли | Що знає |
|---|---|---|
| `bsp/` | crt0.S, lscript.ld, libc_min.c, stubs.c, include/ | старт, пам'ять, адреси |
| `hal/` | драйвери блоків PL | регістри |
| `gfx/` | tft, plot, font5x7 | пікселі, нічого про сигнал |
| `lib/fatfs/` | FatFs + diskio | файлову систему |
| `app/` | екрани, кнопки, SD-сценарії | що показувати |
| `main.c` | стани і головний цикл | усе разом |

Код C-моделі DSP (той самий DSP, що в RTL, але на C) живе окремо, в
`tools/host_sim/model`, і на плату не потрапляє.

### 5.1 `bsp` -- старт без Vitis BSP

- **`lscript.ld`.** Одна область пам'яті `bram` 0x0..0xFFFF (64 КБ): там і
  код, і дані, і стек.
- **`crt0.S`.** Точка входу за адресою 0: ставить стек на 0xFFF0 (вершина
  BRAM, росте вниз) і викликає `main`. На асемблері, щоб жоден пролог
  компілятора не торкнувся стеку раніше. `.data` уже містить початкові
  значення, бо ELF заливається по JTAG.
- **`libc_min.c`.** `memcpy`, `memset` і т.п. Вони позначені `used`, бо з
  `-flto` компілятор інакше викидає їх раніше, ніж до них звернеться
  згенерований ним самим код.
- **`stubs.c`.** Заглушки системних викликів.
- **`include/xparameters.h`.** Базові адреси блоків (розділ 3).
- **`include/xil_io.h`.** `Xil_In32` / `Xil_Out32` -- читання і запис слова
  за адресою через `volatile`.
- **`include/xil_printf.h`.** UART у проєкті немає, тож `xil_printf` --
  заглушка в `stubs.c`, яка нічого не робить.

Прапори CPU в `build_elf.bat` (`-mxl-barrel-shift -mno-xl-soft-mul
-mno-xl-soft-div`) мусять збігатися з конфігурацією MicroBlaze. ELF із ними
не запуститься на старому бітстрімі без цих блоків.

### 5.2 `config.h`

Усі параметри системи в одному місці; таблиця -- у розділі 2.2. Решта
файлів рахує похідні значення з цих чисел під час компіляції.

| Константа | Значення |
|---|---|
| `SPEC_FFT_N`, `SPEC_BINS` | 256, 128 |
| `SPEC_CH_BINS`, `SPEC_BIN0` | -62, 130: вікно спектра навколо каналу |
| `SPEC_LOG_0DBFS` | 224: рівень 0 дБFS |
| `SPEC_WF_SHIFT` | 5: у захопленні рядок = 32 блоки |
| `CFG_LIVE_WF_SHIFT` | 6: у live рядок = 64 блоки |
| `CFG_LIVE_FRAME_MS` | 40: живі екрани оновлюються не частіше ніж раз на 40 мс |
| `CFG_TFT_SCLK_HZ` | 25 МГц |

### 5.3 `main.c` -- стани і головний цикл

**Статичні об'єкти.** Драйвери (`spi`, `tft`, `sys`, `dsp`, `iqs`, `sd_spi`,
`sd`), дані захоплення `cap`, стан переглядача `viewer`, кнопки `keys`,
результати тесту і форматування SD. Динамічної пам'яті немає.

**Чотири стани.**

| Стан | Що відбувається |
|---|---|
| `ST_LIVE` | генератор у залізі, усе в реальному часі (стан за замовчуванням) |
| `ST_PAUSE` | картинка заморожена, працюють zoom і прокрутка |
| `ST_REPLAY` | іде відтворення `SIM.IQ` з картки, на екрані прогрес |
| `ST_STATIC` | готове захоплення з файлу, статичні екрани |

**Допоміжні функції.**

- `millis()` -- мілісекунди з лічильника тактів `TICK`. Різниця тиків
  накопичується в залишку `rem`, тож переповнення 32-бітного лічильника
  (раз на 43 с) не заважає.
- `poll_dsp()` -- викликається драйвером TFT між вікнами довгого малювання
  (`tft.idle`). Демодулятор защіпує лише один результат, тож без цього
  пакет, декодований під час малювання, загубився б.
- `run_sd_test()` -- тест картки. LED1 = ОК, LED2 = помилка. Якщо FAT є,
  файлову систему монтують для replay.
- `live_row(ctx, i)` -- джерело рядків waterfall у live: рядок `i` зверху =
  абсолютний рядок `newest - i` з кільця PL.
- `live_spectra()` -- перед кожним живим кадром FFT або WATERFALL:
  - читає `SPEC_ROWS`;
  - запам'ятовує найновіший рядок і скільки рядків показати (до 192 --
    приблизно висота графіка);
  - FFT-слід = максимум по кожному біну серед рядків, що з'явилися після
    минулого кадру (`live_fft_from`). Так короткий пакет між кадрами не
    проскакує непоміченим.
  - Якщо софт відстав більше ніж на кільце (256 рядків), береться лише
    найновіший рядок.
- `go_live()`:
  - закриває файл;
  - `dsp_rtl_live_start` (генератор, демодулятор з нуля, live-спектр,
    захоплення без очікування);
  - налаштовує `viewer` на живі дані: `cap = 0` до першого вікна, FFT =
    `live_fft`, waterfall з кільця.
- `go_pause()` -- вимикає live-спектр: кільце зберігає останні рядки, і їх
  можна роздивлятися.
- `resume_live()` -- вмикає спектр назад, перезапускає захоплення.
- `start_replay()` -- відкриває `SIM.IQ`, очищає FIFO, перемикає джерело на
  S_AXIS, `dsp_rtl_start(nowait = 1)`: файл записано з першого відліку, тож
  тригер не потрібен.

**`main()`: ініціалізація.**

1. SPI дисплея (перевірка ID), `tft_init` у горизонтальній орієнтації,
   підсвітка.
2. `system_ctrl`, SPI для SD, тест картки.
3. `dsp_rtl_init` (перевірка обох ID і запис конфігурації) і
   `iq_stream_init`. Якщо блок не знайдено -- червоний напис і стоп.
4. Кнопки, `tft.idle = poll_dsp`, `go_live()`.

**`main()`: головний цикл.** Без переривань: опитування по колу.

1. **Кнопки.** `keys_poll` перетворює стан кнопок на дію (5.8).
   - K1+K2 поза live -- назад у live.
   - На екрані SD CARD: K2 коротко -- тест картки і replay `SIM.IQ`, якщо
     він є; K2 затиснута ~3 с (22 повтори) -- форматування картки.
   - У live K2 -- пауза.
   - Решта -- `viewer_key` (наступний екран, zoom, прокрутка).
2. **Завантаження з ПК.** Якщо з ПК по JTAG прийшов файл
   (`sd_iq_upload_poll`), запускається його replay.
3. **PL.**
   - У replay -- `sd_iq_feed` доливає FIFO з файлу.
   - `dsp_rtl_poll` забирає декодований пакет і повертає стан захоплення.
   - Коли захоплення DONE:
     - у live -- копія в `cap` (без спектрів, бо вони йдуть з кільця) і
       одразу новий запуск: наступне вікно пишеться, поки малюється це;
     - у replay -- копія разом зі спектрами (40 рядків + max hold), стан
       STATIC.
   - Під час replay раз на 100 мс оновлюється прогрес.
4. **Екран.**
   - У live не частіше ніж раз на 40 мс: FFT і WATERFALL перемальовуються
     щоразу (`live_spectra`), RAW і BITS -- лише коли прийшло нове вікно
     (раз на ~73 мс).
   - `viewer_draw(full)`: `full = 1` -- з очищенням і рамкою (змінився
     екран або стан), інакше лише вміст поверх старого.
   - `spi_tft_flush` чекає, поки SPI віддасть усе.
   - `stat_frames` і `stat_draw_ms` -- лічильники для вимірювання FPS по
     JTAG.

### 5.4 `hal/dsp_rtl` -- драйвер `dsp_top`

**Константи на початку файлу.** Адреси регістрів (див. 4.2, 4.4) і
значення, пораховані з config.h під час компіляції 64-бітною арифметикою.
Ділення на платі немає.

| Константа | Як рахується |
|---|---|
| `DEMOD_NCO_INC` | `-(канал - LO) / Fs * 2^32` |
| `DEMOD_BIT_INC` | `bitrate * 16 / Fs * 65536` |
| `GEN_RATE_VAL` | `Fs / 100 МГц * 2^32` -- реальний час |
| `GEN_FOFS_VAL` | `(канал - LO + 3 кГц) / Fs * 2^32` |
| `GEN_DEV_VAL`, `GEN_BIT_VAL` | девіація і бітрейт у тих самих одиницях |

**`struct dsp_rtl_t`.** Базова адреса і `dec[2]` -- пакети, декодовані за
поточний запис.

**Функції.**

- `dsp_rtl_init`:
  1. перевіряє ID демодулятора (0x44534D01) і DSP (0x44535001);
  2. soft reset демодулятора;
  3. пише конфігурацію демодулятора, генератора, захоплення, `SPEC_BIN0` і
     межі колонок.
- `dsp_rtl_set_source`: 0x3 -- генератор увімкнено і вибрано; 0x0 --
  S_AXIS.
- `dsp_rtl_start(nowait)` -- одне захоплення для replay:
  1. спектр лише захоплення;
  2. warmup 16384;
  3. демодулятор з нуля і лічильники = 0;
  4. режим (nowait, shift 5);
  5. arm;
  6. enable -- з цього моменту відліки течуть.
- `dsp_rtl_live_start` -- live:
  1. генератор;
  2. демодулятор з нуля і увімкнено;
  3. warmup 1 (демодулятор і так уже працює);
  4. nowait, shift 6;
  5. live-спектр;
  6. arm.
- `dsp_rtl_rearm` -- новий arm без зміни решти. Спектр у live від цього не
  страждає (див. 4.2).
- `dsp_rtl_live_spectrum(on)` -- біт SPEC_CTRL.
- `dsp_rtl_spec_rows` -- лічильник рядків SPEC_ROWS.
- `dsp_rtl_read_row(row)` -- 32 слова з `0x8000 + 128 * (row % 256)`.
- `dsp_rtl_poll`:
  - читає стан захоплення;
  - якщо демодулятор защіпнув результат (STATUS[3]), це пакет (`kind = 0`)
    і йде запис, копіює прапор CRC, кількість байтів і самі байти з пам'яті
    пакета в `d->dec[]`;
  - у будь-якому разі знімає результат (`CTRL = enable | ack`).
- `dsp_rtl_capture_pos` -- CAP_POS для прогресу.
- `copy_words` -- читає n слів і розкладає їх побайтно (байт k -- у бітах
  `8*(k%4)`). Пише по байту, тож призначення не мусить бути вирівняним.
- `dsp_rtl_read_capture(c, spectra)`:
  - декодовані пакети, 384 колонки, кількість пакетів, позиції і біти
    кожного;
  - з `spectra = 1` -- ще 40 рядків waterfall і max hold по них (максимум
    по кожному біну) як FFT захоплення.
- `dsp_rtl_gen_packets`, `dsp_rtl_crc_ok_count` -- лічильники для
  діагностики.

### 5.5 `hal/iq_stream`

- `iq_stream_init` -- перевіряє ID і робить flush.
- `iq_stream_flush` -- CTRL = enable + flush + clear stats.
- `iq_stream_space` -- 1024 мінус рівень.
- `iq_stream_push` -- n записів у DATA.
- `iq_stream_popped` -- скільки відліків забрав DSP.

### 5.6 `hal/spi_tft`, `gfx/tft` -- дисплей

**`hal/spi_tft.c`** -- байти на шину.

- `spi_tft_init` -- перевіряє ID, рахує дільник
  `div = aclk / (2*sclk) - 1` (= 1 для 25 МГц), вмикає ядро з
  автоматичним CS.
- `spi_tft_hw_reset` -- RST дисплея на 10 мс, потім 120 мс очікування.
- `spi_tft_backlight` -- біт підсвітки.
- `spi_tft_flush` -- чекає порожнього FIFO і кінця передачі.
- `set_dc` -- DC можна міняти лише між байтами, тому спершу flush.
  Якщо DC вже правильний, нічого не робить.
- `spi_tft_put`, `spi_tft_write` -- байт або масив з очікуванням місця.
- `spi_tft_cmd` -- байт команди (DC = 0) і аргументи (DC = 1).
- `fifo_room16` -- скільки пікселів (по 2 байти) влізе у FIFO зараз.
- `spi_tft_repeat16` і `spi_tft_write16` -- головні функції для швидкості:
  пікселі (RGB565, старший байт першим) пишуться пачками по стільки, скільки
  є місця. Статус читається раз на пачку, а не на кожен байт. Так шина AXI
  не стає вузьким місцем, і 25 МГц SCLK використовуються майже повністю.

**`gfx/tft.c`** -- рівень ST7789.

- `tft_init` -- апаратний скид, SWRESET (150 мс), SLPOUT (120 мс), COLMOD
  0x55 (16 біт на піксель), орієнтація, INVON (інверсія -- особливість цієї
  панелі), NORON, DISPON.
- `tft_set_rotation` -- регістр MADCTL (дзеркала MX / MY, обмін осей MV,
  порядок BGR) і розміри. Панель 240x320 стоїть у RAM контролера зі
  зсувом, що залежить від повороту (`x_off` / `y_off`). Прошивка
  використовує `TFT_ROT_90`: 320x240.
- `tft_set_window` -- CASET і RASET задають прямокутник, RAMWR -- далі
  йдуть пікселі. Контролер сам переходить на наступний рядок прямокутника.
- `tft_fill_rect` -- вікно і один колір `w*h` разів. На ньому побудовано
  `clear`, `pixel`, лінії і рамки.
- `tft_draw_char` / `tft_draw_text` -- шрифт 5x7 (`font5x7.c`, ASCII
  0x20..0x5F: лише великі літери, малі виводяться як `?`) з масштабом. Кожен символ -- окреме вікно, фон малюється
  разом із символом, тож старий текст затирається без очищення.
- `tft_push_rect` -- готовий масив пікселів `w x h` в одне вікно. Перед
  кожним вікном викликає `tft->idle` (див. 5.3).

**Чому немає мерехтіння.** Екрани ніколи не очищають область графіка перед
малюванням (крім першого кадру після зміни екрана). Кожна колонка або
рядок будується в RAM повністю -- фон, сітка, слід -- і йде одним вікном
поверх старої. Глянути "напівнамальований" кадр око не встигає.

### 5.7 `gfx/plot` -- примітиви графіків

- `plot_area` -- область графіка: x 6.., y 28.., ширина `w-12`, висота
  `h-44` (зверху заголовок, знизу підписи осі).
- `plot_u32_to_str`, `plot_text_w` (6 пікселів на символ), `plot_text_pad`
  -- текст, доповнений пробілами до n символів, щоб затерти довшу стару
  мітку.
- **Колонка** `plot_col_t` -- масив до 240 пікселів одного стовпця:
  - `plot_col_fill` -- фон;
  - `plot_col_span` -- вертикальний відрізок з обрізанням;
  - `plot_col_dot` -- точка;
  - `plot_col_send` -- стовпець одним вікном 1 x h.
- **`plot_scratch`** -- спільна робоча пам'ять екранів (union). Малює завжди
  лише один екран, а BRAM мало, тому та сама пам'ять -- то колонка для
  RAW / BITS, то масиви сліду FFT, то таблиця кольорів і рядок waterfall.
- `plot_axis_box`, `plot_legend`, `plot_series_*`, `plot_vline_clipped` --
  старіші загальні примітиви. Поточні екрани ними не користуються, їх
  тримає host_sim.

### 5.8 `app/viewer`, `keys`, `zoom` -- екрани і кнопки

**`keys.c` -- дві кнопки, коротко / довго / разом.**

| Подія | Дія |
|---|---|
| K1 коротко | `KEY_NEXT`, наступний екран |
| K2 коротко | `KEY_ZOOM` |
| K1 затиснута | `KEY_PAN_BACK` -- через 400 мс, далі кожні 120 мс |
| K2 затиснута | `KEY_PAN_FWD` -- так само |
| K1+K2 разом | `KEY_BOTH` один раз, потім нічого, поки обидві не відпущено (`chord`) |

Коротка дія спрацьовує на відпусканні. Тому утримання ніколи не дає ще й
"короткого" ефекту.

**`zoom.c` -- видиме вікно над n точками.**

- Рівень 0..4 (x1, x2, x4, x8, x16), `off` -- перша видима точка.
- `zoom_cycle` -- наступний рівень, центр вікна зберігається.
- `zoom_pan` -- зсув на 1/8 вікна, з упором у краї.

У кожного екрана свій `zoom_t`.

**`viewer.c` -- стан переглядача.**

- `viewer_t`:
  - поточний екран (`mode`) і стан (`STATIC` / `LIVE` / `PAUSE`);
  - zoom кожного екрана;
  - вказівник на захоплення (`cap`), на FFT-слід (`fft`) і його підпис
    ("LIVE", "PAUSE", "MAX HOLD");
  - джерело рядків waterfall (`wf`, див. 5.10);
  - прогрес запису, текст джерела, результати SD-тесту.
- `viewer_key`:
  - `KEY_NEXT` перемикає екран завжди;
  - zoom і прокрутка -- лише поза live і не на екрані SD.
- `viewer_use_capture` -- для STATIC: FFT = max hold захоплення, waterfall =
  його 40 рядків (найстаріший зверху), тривалість 72.8 мс.
- `draw_frame` -- для `full`:
  - очищення і зелена рамка;
  - назва екрана великим шрифтом;
  - позначка LIVE (зелена) або PAUSE (жовта);
  - рівень zoom;
  - номер екрана "n/5";
  - підказка про кнопки, своя для кожного стану.
- `draw_capture_progress` -- поки немає захоплення: напис CAPTURE,
  смужка прогресу, назва джерела.
- `viewer_draw` -- у live zoom ігнорується (завжди вся картинка); далі
  виклик потрібного екрана.

### 5.9 `app/view_time` -- RAW I/Q і BITS

Обидва екрани мають вісь часу над 384 колонками захоплення і малюються
стовпець за стовпцем через `plot_col_t`.

**Допоміжні.**

- `x_to_sample` -- номер відліку захоплення для пікселя x з урахуванням
  zoom. Лише 32-бітна арифметика: 64-бітне ділення тягне велику функцію
  libgcc.
- `sample_to_x` -- обернене, або -1.
- `ms_label`, `time_axis` -- час початку і кінця видимого вікна під
  графіком.
- `packet_cols`, `packet_dots`, `packet_labels` -- біла пунктирна лінія і
  "P1" / "P2" на початку кожного пакета.

**`view_raw`.**

1. Масштаб -- найбільше |значення| по всіх 384 колонках, +1/8. Однаковий для
   I і Q і для будь-якого zoom.
2. Дві смуги -- I (бірюзова) і Q (жовта).
3. Для кожного пікселя береться колонка захоплення під ним. Стовпець
   будується так: чорний фон, рамка і перехрестя (`box_column`), пунктир
   пакета, вертикальний відрізок від min до max. Відрізок з'єднується з
   попереднім стовпцем, тому лінія без розривів.

Видно шум між пакетами і "товсту" синусоїду пакетів.

**`view_bits`.**

- **Верхня смуга, 76 px -- осцилограма бітів.** `bit_at(s)` для відліку `s`
  знаходить пакет і номер біта:
  `(s - first_bit + T/2) * 64 / T`, де `T` -- бітовий період у 1/64
  відліку. Повертає 0, 1 або -1 поза пакетами. Лінія зелена в пакеті, сіра
  посередині поза ним.
- **Нижче -- текст для кожного з двох пакетів.**
  - Скільки біт записано.
  - Якщо демодулятор знайшов sync -- "CRC OK" (зелений) або "CRC ERROR"
    (червоний), перші 10 байт як текст (`"DF5 PKT07 "`) і до 25 байт у hex.
  - Інакше -- "NO SYNC" і сирі біти слайсера в hex.
  - Кожен рядок доповнено пробілами до повної ширини.

### 5.10 `app/view_freq` -- FFT і WATERFALL

Обидва екрани мають вісь частоти над 128 бінами.

- `bin_khz(b)` -- частота біна `b` вікна в кГц:
  `LO + (SPEC_CH_BINS + b - 64) * Fs / 256`.
- `khz_label` -- рядок "866.310M".
- `freq_axis` -- три мітки під графіком: лівий край, центр і правий край
  видимого вікна (з урахуванням zoom).

**`view_fft`.**

1. Область 282 x 193 px. Праворуч підписи дБ (0 ... -100, сітка 10 дБ на
   поділку), малюються лише при `full`.
2. **Слід.** Для кожного пікселя x рівень інтерполюється між двома
   сусідніми бінами (`fr`/256), переводиться в y (`level_y`: рівень ->
   десяті дБ (`* 241/64`) -> пікселі). Щоб лінія була суцільною, для
   кожного x запам'ятовується відрізок від попереднього y до поточного
   (`t_lo` / `t_hi`).
3. **Сітка.** 11 колонок і 11 рядків. Їхні позиції обчислюються один раз,
   а не діленням на кожен піксель.
4. **Малювання.** Одне вікно на всю область, рядок за рядком: фон -> сітка ->
   слід. `tft->idle` викликається кожні 16 рядків.
5. **Пік.** Найбільший бін у видимому вікні: білий квадрат і жовтий напис
   "PK 866.310M -12.3DBFS". У кутку -- підпис сліду (LIVE / PAUSE / MAX
   HOLD).

**`view_waterfall`.**

- **Джерело рядків -- `wf_src_t`.** Функція `row(ctx, i)` повертає i-тий
  рядок зверху. Так один код малює і 40 рядків захоплення (найстаріший
  зверху, мітки "0MS" і "72.8MS"), і живе кільце PL (найновіший зверху,
  "NOW" і "-691MS").
- **Шкала кольорів.**
  - `lo` = середній рівень усіх видимих рядків + 4 (трохи вище шуму), `hi` =
    максимум.
  - Таблиця 256 кольорів: нижче `lo` -- темно-синій; далі синій -> блакитний
    -> білий (`wf_color`).
- `xbin[x]` -- бін для кожного пікселя (з zoom), рахується один раз.
- **Малювання.** Одне вікно, рядок екрана за рядком. Рядок даних, що
  потрапляє на рядок екрана, -- `y * nrows / h`. Якщо він той самий, що
  попередній, готовий рядок пікселів просто відправляється ще раз.
- **Мітки пакетів.** Для захоплення праворуч ставляться мітки "<P1",
  "<P2" -- там, де почалися пакети.

Осі: x -- частота (зліва нижча), y -- час.

### 5.11 SD-карта: від SPI до файлу

**`hal/axi_qspi.c` -- IP Xilinx як простий байтовий SPI.**

- `axi_qspi_init`:
  - програмний скид ядра;
  - режим: майстер, SPI mode 0, ручний SS;
  - скид FIFO;
  - SS неактивний.
- `axi_qspi_select` -- регістр SSR: біт 0 = 0 вибирає картку.
- `axi_qspi_xfer`:
  - повнодуплексна передача шматками по 16 байт (розмір FIFO): спершу всі
    байти в DTR, потім стільки ж прочитати з DRR;
  - на кожен байт є тайм-аут опитування. Якщо байт так і не прийшов,
    читається 0xFF і росте лічильник `timeouts` -- захист від зависання.

**`hal/sd_card.c` -- протокол SD у режимі SPI (SD Physical Layer
Simplified Spec, глава 7).**

- `command` -- кадр команди з 6 байт (з CRC для CMD0 / CMD8) і очікування
  відповіді R1.
- `sd_init`:
  1. ≥ 74 такти з невибраною карткою;
  2. CMD0 (у SPI-режим, до 10 спроб);
  3. CMD8 (перевірка напруги: відповідь 0x1AA означає SD v2, illegal --
     v1);
  4. ACMD41 у циклі до ~1 с (картка виходить з idle; для v2 з HCS);
  5. CMD58 (OCR: біт CCS = SDHC, адреса в блоках, а не байтах);
  6. для старих карток CMD16 (блок 512);
  7. CMD13 (якщо картка заблокована паролем -- `SD_ERR_LOCKED`);
  8. CMD9 (CSD -> ємність за формулами CSD v1 / v2).
- `sd_read` -- CMD17 і токен 0xFE, 512 байт, 2 байти CRC.
- `sd_write` -- CMD24, токен, дані; чекати "data accepted" і поки картка
  зайнята.

**`lib/fatfs/` -- FatFs R0.15a.**

- `ffconf.h`: запис дозволено, `f_mkfs` є, лише короткі імена 8.3,
  `FF_FS_TINY` (один буфер сектора на том -- економія RAM).
- `diskio.c` -- міст FatFs -> `sd_card`: `disk_initialize` викликає
  `sd_init`, `disk_read` / `disk_write` -- блоки по одному.
  `diskio_sd_attach` вказує, яку картку використовувати.

**`app/sd_test.c` -- діагностика без FatFs** (для екрана SD CARD).

1. `sd_init`.
2. Блок 0: якщо це одразу FAT boot sector -- без MBR, інакше з таблиці
   розділів береться початок першого розділу.
3. З boot sector: розмір кластера, FAT16 чи FAT32, мітка тому, де корінь.
4. Перші 8 записів кореня (імена, розміри, папки).
5. Швидкість послідовного читання в КБ/с (~450).

**`app/sd_format.c`.**

- `f_mkfs` (FAT32; для малих карток -- як вирішить FatFs).
- Монтування.
- Запис `DF5TEST.TXT`, читання назад і порівняння.
- Результат -- на екран SD CARD.

**Стирає всю картку.**

**`app/sd_iq.c` -- файли I/Q.**

- `sd_iq_mount` -- `f_mount`, а також ставить магічне слово
  "UPLD" у поштову скриньку.
- **Replay.**
  - `sd_iq_open` -- відкриває файл; кількість відліків = розмір / 4.
  - `sd_iq_feed` -- поки є місце в FIFO: якщо буфер 4 КБ спорожнів,
    читається наступний шматок файлу (лише цілі пари I/Q); з буфера в FIFO
    йде стільки, скільки влізе. Повертає 1 в кінці файлу.
  - Картка дає ~450 КБ/с, а реальний час потребує 18 МБ/с. Тому replay
    іде повільніше, але DSP від темпу не залежить.
- **Завантаження з ПК (JTAG).**
  - `sd_iq_box` -- структура в RAM: magic, команда, довжина, статус,
    скільки записано, буфер 4 КБ.
  - Скрипт `tools/sd_upload.py` знаходить її адресу в ELF і через `xsct`
    пише туди команди: CREATE (ім'я файлу), WRITE (шматок), CLOSE.
  - `sd_iq_upload_poll` у головному циклі виконує команду через FatFs, пише
    статус і обнуляє `cmd` -- це знак скрипту, що можна слати далі.
  - Після CLOSE прошивка одразу запускає replay нового файлу.
  - Той самий буфер служить і для replay, тому CREATE спершу закриває
    replay.

**`app/view_sd.c`.** Екран SD CARD показує результат тесту (тип картки,
ємність, FAT, мітку, файли, швидкість) і результат форматування.
`view_sd_formatting` -- напис на час форматування.

## 6. Що відбувається в часі

### 6.1 Увімкнення

1. `scripts/run_board.tcl` (xsct) заливає бітстрім, потім ELF через JTAG
   (`mdm`) і запускає процесор.
2. `main()`: дисплей, тест SD, конфігурація DSP, `go_live()`.
3. Перший кадр: поки перше вікно захоплення (72.8 мс) не записане, RAW і
   BITS показують смужку прогресу. FFT і WATERFALL починають малюватися,
   щойно в кільці з'явився перший рядок (3.6 мс).

### 6.2 Один живий кадр (наприклад, WATERFALL)

```
PL, безперервно:  iq_gen -> 4.5 МВід/с -> демодулятор (пакети, CRC)
                                       -> FFT кожних 256 відліків -> рядок кожні 64 блоки (3.64 мс)
                                       -> захоплення 72.8 мс -> DONE

MicroBlaze, цикл:  кнопки -> dsp_rtl_poll (пакет? захоплення DONE? -> копія + rearm)
                   -> пройшло 40 мс? -> live_spectra(): SPEC_ROWS, рядки з кільця
                   -> view_waterfall(): 192 рядки кільця -> пікселі -> SPI 25 МГц
```

Обмежує кадр SPI дисплея: область графіка FFT -- 282 x 193 пікселі по 2
байти ≈ 109 КБ, на 25 МГц це ≈ 35 мс. Виміряно на платі: RAW 14 кадрів/с, BITS 13.7, FFT 15.7, WATERFALL
15.3. Демодулятор при цьому декодує всі пакети (59/59 з CRC OK за 2 с).

### 6.3 Пауза

K2: `SPEC_CTRL.live = 0`. Кільце більше не пишеться, генератор і
демодулятор працюють далі. Екрани показують заморожене кільце і останнє
вікно захоплення; zoom і прокрутка працюють. K1+K2: спектр знову live,
захоплення перезапускається.

### 6.4 Replay файлу

На екрані SD CARD натиснути K2 (або завантажити файл з ПК):

1. Перевірка картки, відкриття `SIM.IQ`, FIFO очищено, джерело -- S_AXIS,
   `dsp_rtl_start(nowait)`.
2. Цикл: `sd_iq_feed` доливає FIFO, DSP приймає відліки по мірі появи (і
   стоїть, коли FIFO порожній).
3. Через 16384 + 327680 відліків (~1.3 МБ файлу, кілька секунд) захоплення
   DONE.
4. Копія з 40 рядками спектра. Екрани STATIC з "MAX HOLD".

## 7. Як це перевіряється

- **`vivado/sources/tb/tb_dsp_top.sv`** + `scripts/sim_tb.bat` (xsim) --
  весь `dsp_top` через AXI:
  - T1 -- ID і значення після скиду;
  - T2 -- генератор -> демодулятор: кожен пакет з CRC OK і правильними
    байтами;
  - T4 -- захоплення з генератора: 2 пакети по ~464 біти;
  - T3 -- `sim.iq` через S_AXIS + захоплення, дамп усього захопленого;
  - T5 -- live-спектр: рядки йдуть по колу, пакет видно на каналі.
- **`tools/check_dsp_capture.py`** звіряє дамп T3 з Python-копією
  C-алгоритму. Колонки і waterfall мають збігтися біт у біт, а в бітах
  кожного пакета має знайтися кадр із `sim.iq.json` без помилок.
- **`tools/demod_model.py`** -- еталонна модель демодулятора. RTL
  збігається з нею один в один.
- **`tools/host_sim/`** -- ті самі екрани (`vitis/src/app`, `gfx`), зібрані
  для ПК:
  - замість SPI -- емулятор ST7789 (`st7789_emu.c`), що малює в PPM;
  - замість PL -- C-модель DSP (`model/dsp`, `model/source`);
  - `golden.md5` -- контрольні суми картинок, щоб помітити, що зміна в
    коді випадково змінила екран.
- **На платі** -- `scripts/dsp_dump.tcl` читає регістри і пам'ять `dsp_top`
  через JTAG (стан, пакети, рядки waterfall), а `stat_frames` /
  `stat_draw_ms` дають FPS.
