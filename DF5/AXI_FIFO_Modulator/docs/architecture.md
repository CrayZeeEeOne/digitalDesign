# DF5: як влаштований проєкт і що в ньому відбувається

Документ для того, щоб розуміти проєкт повністю: від заліза до кожного графіка на екрані.
Читати по порядку; стан і історія версій — у [`../STATUS.md`](../STATUS.md).

---

## 1. Що це за проєкт одним абзацом

На платі PA35T-StarLite (FPGA Xilinx Artix-7 `xc7a35t`) всередині FPGA зібраний маленький комп'ютер:
процесор **MicroBlaze** + пам'ять + два самописні периферійні блоки (SPI для дисплея і блок кнопок).
На цьому процесорі працює програма на C, яка **генерує радіосигнал** (I/Q-відліки FSK-пакетів),
**демодулює** його (повторює те, що робить радіоприймач), **записує** результат і **малює графіки**
на маленькому TFT-дисплеї ST7789. Кнопками перемикаються графіки, зум і прокрутка.

Окремо в проєкті є **апаратний демодулятор на Verilog (RTL)**, який робить те саме, але логікою
в FPGA. Він поки що перевірений лише в симуляції і на плату не поставлений.

Постановка задачі (ТЗ) — [`../../readme.md`](../../readme.md), три блоки:

| Блок | Що треба | Стан |
|---|---|---|
| 1. TFT | SPI-контролер у RTL + C-драйвер, тест на екрані | працює на платі |
| 2. SD-карта | читати файли через готовий IP + FatFs | не почато |
| 3. I/Q replay | читати I/Q-файл із SD, демодулювати, показувати графіки | графіки і демодуляція є, але на синтетичному сигналі, не з SD |

## 2. Залізо

### 2.1 Що фізично є на платі

```
                 PA35T-StarLite
  ┌──────────────────────────────────────────────────┐
  │  генератор 200 МГц (диференційний, R4/T4)        │
  │  кнопки K1 (W21), K2 (Y21), активні нулем        │
  │  USB-UART CH340E (P14/P15) — у дизайні НЕ використ.│
  │  JTAG — через нього заливаємо все з ПК           │
  │                                                   │
  │  роз'єм JM1 ──шлейф──> TFT ST7789 320×240         │
  │     SCL E16, SDA F13, RES D16, DC F14,            │
  │     CS C13, BLK (підсвітка) D14                   │
  └──────────────────────────────────────────────────┘
```

Піни описані у [`../vivado/constraints/tft.xdc`](../vivado/constraints/tft.xdc).

### 2.2 Що зібрано всередині FPGA (Block Design `microblaze`)

```
  200 МГц ──> clk_wiz ──> 100 МГц ─────────────── такт усього нижче
                                │
   ┌────────────────────────────┴───────────────────────────┐
   │                                                        │
   │   MicroBlaze (32-біт процесор)                         │
   │     │ LMB (швидка шина пам'яті)                        │
   │     └──> BRAM 32 КБ  (0x0000_0000 – 0x0000_7FFF)       │
   │     │                                                  │
   │     │ AXI4-Lite (шина периферії)                       │
   │     └──> AXI interconnect                              │
   │             ├──> tft_top      (0x0001_0000) ──> пінів TFT
   │             └──> system_ctrl  (0x44A1_0000) <── кнопки │
   │                                                        │
   │   MDM (debug module) <──> JTAG: заливка ELF, стоп/старт│
   └────────────────────────────────────────────────────────┘
```

Пояснення термінів:

* **MicroBlaze** — процесор, зібраний з логіки FPGA (soft-core). Без кешів і без апаратного
  множника: кожне множення — це підпрограма `__mulsi3` (десятки тактів). Тому DSP на ньому повільний.
* **BRAM** — блокова пам'ять усередині FPGA. Тут 32 КБ, і це **вся** пам'ять процесора: код,
  змінні і стек разом. Звідси постійна боротьба за байти.
* **LMB** — пряма шина процесор↔BRAM, 1 такт на доступ.
* **AXI4-Lite** — проста шина «записати/прочитати 32-бітний регістр за адресою». Кожен
  периферійний блок — це набір регістрів, які процесор читає/пише як звичайну пам'ять.
* **MDM** — модуль відладки. Через нього XSCT (інструмент Xilinx) по JTAG заливає програму в BRAM,
  зупиняє процесор, читає регістри (так я перевіряю «процесор працює»).

Файл, з якого цей BD будується: [`../scripts/create_bd.tcl`](../scripts/create_bd.tcl).
Таймінг закрито на 100 МГц з великим запасом (WNS ≈ +3.8 нс), зайнято ~7 % LUT.

### 2.3 Периферія: регістри

**`tft_top` / `spi_tft_ctrl.sv` (0x0001_0000)** — байтовий SPI-передавач до дисплея.
Детально — [`block1_tft.md`](block1_tft.md).

| Зсув | Регістр | Що робить |
|---|---|---|
| 0x00 | CTRL | біти: enable, DC (0 = команда, 1 = дані), RST_N дисплея, CS, авто-CS, BLK (підсвітка) |
| 0x04 | CLKDIV | частота SPI: 100 МГц / (2·(CLKDIV+1)); у нас 3 → 12.5 МГц |
| 0x08 | TXDATA | запис байта в FIFO на 16 байт |
| 0x0C | STATUS | busy, FIFO повний/порожній, рівень |
| 0x10 | ID | 0x5F778901 — щоб софт переконався, що блок на місці |

Уся «розумність» дисплея — у C-драйвері: RTL лише виштовхує байти по SPI.

**`system_ctrl_top` / `system_ctrl_regs.sv` (0x44A1_0000)**

| Зсув | Регістр | Що робить |
|---|---|---|
| 0x08 | BTN_RAW | стан кнопок після антидребезгу (8 мс), 1 = натиснута |
| 0x0C | BTN_EVENT | защіпнуті натискання/відпускання (скидаються записом 1) |
| 0x18 | TICK | лічильник тактів 100 МГц — з нього прошивка рахує мілісекунди |
| 0x04, 0x10, 0x14 | LED, дільник SD-SPI, CS SD | заготовка під Блок 2 |

## 4. Як усе збирається і потрапляє на плату

```
  ┌─────────────── залізо (Vivado) ───────────────┐   ┌──── програма (mb-gcc) ────┐
  build.bat -all                                      build_elf.bat
    build.tcl: проєкт + RTL + xdc                       bsp/crt0.S + bsp/stubs.c
      create_bd.tcl: Block Design                       src/main.c + src/*/ *.c
      patch_…buttons.tcl                                bsp/lscript.ld (32 КБ)
    run.tcl: синтез → імплементація → .bit → .xsa       -Os -flto
                     │                                            │
                     ▼                                            ▼
     vivado/project/…/microblaze_wrapper.bit          vitis/elf/df5_app.elf
                     └──────────────┬─────────────────────────────┘
                                    ▼
                       run_board.tcl (XSCT по JTAG):
                         1. fpga -file .bit   → FPGA стає «комп'ютером»
                         2. rst -processor
                         3. dow .elf          → програма в BRAM
                         4. con               → процесор стартує з адреси 0
```

Важливі деталі:

* **Бітстрім і програма окремо.** Бітстрім описує залізо, ELF — програму. Програма не вшита в
  бітстрім, тому після вимкнення живлення плата «порожня», і `run_board.tcl` треба запускати знову.
* **Без Vitis-платформи.** Зазвичай Xilinx генерує купу BSP-файлів. Тут замість цього три маленькі:
  * `bsp/crt0.S` — перші 4 інструкції: поставити стек на `0x7FF0` і викликати `main`;
  * `bsp/lscript.ld` — розклад пам'яті: код і дані з адреси 0, стек зверху; лінкер **падає**,
    якщо під стек лишається менше 1 КБ;
  * `bsp/include/xparameters.h` — адреси периферії (мають збігатися з `create_bd.tcl`).
* **`-flto`** (link-time optimization): компілятор бачить усю програму разом і вбудовує дрібні
  функції. Без нього код не влазить у 32 КБ.
* **`build.bat -board`** робить усе вище одним махом.

## 5. Прошивка: шари

> **Оновлення (гілка `dsp-rtl`):** обробка сигналу тепер у PL (`docs/dsp_rtl.md`). Папки
> `dsp/` і `source/`, описані нижче, перенесено з `vitis/src` у `tools/host_sim/model/` --
> це C-модель для host-симулятора, у прошивку вона не входить.

```
             main.c                    ← головний цикл
               │
             app/                      ← «застосунок»: запис, екрани, кнопки
            ╱  │   ╲
     source/  dsp/  gfx/               ← джерело сигналу │ обробка │ малювання
                     │
                    hal/               ← драйвери регістрів у FPGA
                     │
                    bsp/               ← старт, пам'ять, адреси
```

Правило: **кожен шар знає лише про шари під собою.** `dsp/` нічого не знає про дисплей, тому
його можна зібрати на ПК і перевірити. `gfx/` нічого не знає про радіо.

| Папка / файл | Що там |
|---|---|
| `config.h` | **усі** параметри: Fs = 4.5 МГц, частоти, бітрейт, розмір блоку 256, довжина запису |
| `main.c` | ініціалізація + нескінченний цикл (§6) |
| `source/iq_source.h` | інтерфейс «дай мені n відліків I/Q» — щоб джерело можна було підмінити |

| `dsp/nco_mixer.c` | зсув частоти (§7.2) |
| `dsp/decimator.c` | зниження частоти дискретизації в 16 разів (§7.3) |
| `dsp/discriminator.c` | миттєва частота (§7.4) |
| `dsp/burst_detect.c` | «тут пакет / тут тиша» (§7.5) |
| `dsp/bit_decoder.c` | біти (§7.6) |
| `dsp/demod_chain.c` | зшиває 5 блоків вище в один ланцюг |
| `dsp/fft.c`, `dsp/spectrum.c` | FFT 256 точок, спектр (§7.7) |
| `dsp/dsp_math.c`, `dsp_tables.c` | синус і вікно Ханна (таблиці згенеровані `tools/gen_mem.py`) |

| `app/view_time.c` | екрани RAW I/Q і BITS |

## 6. Що відбувається від увімкнення до картинки

```
_start (crt0.S)
  └─ main()
       spi_tft_init      перевіряє ID = 0x5F778901 (блок на місці?)
       tft_init          скид дисплея, режим 16 біт/піксель, поворот 90° → 320×240
       підсвітка ON, system_ctrl_init, src_synth_init, viewer_init, keys_init

       ЦИКЛ:
       ┌─ поки запис не готовий:
       │     src_synth  → 256 відліків I/Q у буфер iq[]
       │     viewer_process_block:
       │        для кожного відліку: demod_chain_step → capture_sample
       │        для блоку:           capture_block (FFT)
       │     кожні 64 блоки — перемалювати прогрес «CAPTURE»
       └─ коли запис готовий:
             keys_poll (кнопки + мілісекунди з TICK)
             якщо дія → viewer_key (екран / зум / прокрутка) → перемалювати
```

Стани запису (`capture.c`):

```
 WARMUP ──16 384 відліки──> WAIT ──кінець пакета──> RECORD ──163 840 відліків──> DONE
 (≈3.6 мс: оцінки рівнів        (чекаємо паузу,             (36.4 мс: рівно
  стабілізуються)                щоб запис почався в ній)     2 пакети)
```

Після `DONE` процесор лише опитує кнопки й перемальовує екран із збережених даних. Генератор
більше не викликається — **картинка статична**.

## 7. Сигнальний ланцюг: що саме рахується

### 7.0 Що таке I/Q (коротко)

Радіоприймач переносить сигнал біля несучої (тут умовно 868.5 МГц) на «нуль» і віддає два потоки
чисел: **I** і **Q**. Пара (I, Q) — це комплексне число: його довжина — амплітуда, кут — фаза.
Сигнал, що обертається проти годинникової стрілки, має додатну частоту відносно центру, за
годинниковою — від'ємну. Так одним потоком видно частоти від −Fs/2 до +Fs/2.
Тут **Fs = 4.5 МГц** — 4.5 млн пар (I, Q) за секунду, кожне число `int16`.

### 7.1 Джерело: `src_synth.c`

Генерує те, що прийшло б з антени:

* **2-FSK**: біт 1 = частота −200 кГц, біт 0 = −300 кГц (несуча каналу −250 кГц від центру,
  девіація ±50 кГц). Амплітуда 3000.
* **19 200 біт/с** → один біт = 4.5 МГц / 19 200 ≈ **234 відліки**.
* **Пакет** 192 біти (≈10 мс): 32 біти преамбули 0101…, далі псевдовипадкові біти.
  **Пауза** 128 біт (≈6.7 мс). Цикл ≈16.7 мс.
* **Шум** ±128 на I і Q завжди (≈28 дБ нижче сигналу).

### 7.2 Мікшер NCO: `nco_mixer.c`

Множить кожен відліч на e^(+jθ), де θ росте на `inc` кожен відлік. Це зсуває **весь спектр** на
+250 кГц, тож канал (−250 кГц) опиняється на 0 Гц. `inc` = 250 кГц / 4.5 МГц · 65536 ≈ 3641.
(До v0.4.3 тут було переповнення і мікшер стояв на +53 кГц.)

### 7.3 Децимація: `decimator.c`

Усереднює кожні 16 відліків в один → нова частота 4.5 МГц / 16 = **281.25 кГц**, і заодно
відрізає все далеке від 0 Гц (шум, сусідні сигнали). Біт тепер ≈ **14.6 відліків**.
Далі все працює на цій частоті — у 16 разів менше обчислень.

### 7.4 Дискримінатор: `discriminator.c`

Для пари сусідніх відліків рахує, на який кут повернувся вектор (I, Q): це **миттєва частота**.
Формула — векторний добуток `i·q_prev − q·i_prev`. Під час біта 1 вона одного знаку, біта 0 —
іншого. Так FSK перетворюється на «майже цифровий» сигнал.

### 7.5 Детектор пакета: `burst_detect.c`

* `pavg` — згладжена потужність (|I| + |Q|);
* `noise` — згладжений рівень у паузах (під час пакета заморожується);
* **пакет є**, коли `pavg > 1.5 · noise` (мінімум 700);
* пакет **кінчається** лише після 16 відліків нижче порогу підряд — щоб короткі провали не рвали пакет.

### 7.6 Декодер бітів: `bit_decoder.c`

Три кроки, як у RTL:

1. **AFC** — повільне середнє миттєвої частоти = поріг рішення (компенсує розстройку).
2. **Слайсер** — біт = чи частота вище порогу.
3. **Відновлення такту** — лічильник фази росте на 4474 за відлік (= 19 200 біт/с при
   281.25 кГц); коли переповнюється — це **середина біта**, беремо рішення. На кожній зміні
   0↔1 фаза підтягується до половини, щоб рішення не «з'їжджали».

Результат: 192 біти пакета без помилок (перевіряється на ПК, §9). Наприкінці ≈3 зайві біти:
детектор помічає кінець пакета з запізненням. Пошуку синхрослова і CRC поки немає — тестовий
сигнал їх не має.

### 7.7 Спектр: `spectrum.c`, `fft.c`

На кожен блок із 256 відліків:

1. вікно **Ханна** (згладжує краї блоку, щоб не було «хвостів» у спектрі);
2. **FFT 256 точок** → 256 «бінів» по 4.5 МГц / 256 ≈ **17.6 кГц**;
3. беремо **128 центральних** бінів: ±1.125 МГц;
4. рівень у логарифмі: одиниця = 0.376 дБ, **0 dBFS** = синус на повну шкалу АЦП.

### 7.8 Що зберігає запис: `capture.c`

Сирі 163 840 відліків у 32 КБ не влізуть, тому зберігається лише підсумок:

| Дані | Розмір | Як отримано |
|---|---|---|
| `raw[384]` | 1.5 КБ | на кожну з 384 колонок часу — min/max I і Q, крок 64 одиниці |
| `pkt[2]` | ≈90 Б | для кожного пакета: де почався/скінчився, біти |
| `wf[40][128]` | 5 КБ | waterfall: 40 рядків; кожен = середній спектр 16 блоків (4096 відліків ≈ 0.9 мс) |
| `fft[128]` | 128 Б | для екрана FFT: **максимум** по 40 рядках (max hold) |

Детально про пам'ять — [`graph_data_storage.md`](graph_data_storage.md).

## 8. Екрани і кнопки

| # | Екран | Звідки дані | Що на ньому |
|---|---|---|---|
| 1 | RAW I/Q | `raw[]` | обвідна I (зверху) і Q (знизу); широкі смуги — пакети, тонкі — шум у паузах; позначки P1/P2 |
| 2 | BITS | `pkt[]` | біти як хвиля 0/1 у часі + по рядку hex на пакет |
| 3 | FFT | `fft[]` | жовта лінія, сітка 10 дБ, 0…−100 dBFS; маркер піку; «MAX HOLD» |
| 4 | WATERFALL | `wf[]` | x — частота, y — час (0 мс зверху), колір — рівень (синій = шум, білий = сильний) |

Кнопки (`keys.c`, `zoom.c`):

* **K1 коротко** — наступний екран; **K2 коротко** — зум ×1 → ×2 → ×4 → ×8 → ×16 → ×1;
* **утримати K1** — прокрутка назад, **утримати K2** — вперед (через 0.4 с, далі кожні 0.12 с);
* коротке натискання спрацьовує **на відпусканні**, тож утримання ніколи не перемикає екран;
* у кожного екрана свій зум і позиція; часові екрани зумлять час, частотні — частоту.

## 10. RTL-демодулятор (поки лише симуляція)

Те саме, що §7, але як логіка в FPGA — один відлік за такт:

```
AXI-Stream I/Q → demod_nco_mixer → demod_cic3 (/16) → demod_discriminator (CORDIC)
              → demod_power (детектор пакета) → demod_bit_decoder
                (AFC, слайсер, такт, преамбула, sync 0x91D3, байти, CRC-16) → пам'ять пакета
```

Обв'язка: `rtl_demod_regs` (регістри AXI4-Lite), `iq_stream_*` (FIFO: MicroBlaze пише I/Q →
потік у демодулятор). **У Block Design їх ще немає** — це крок до Блоку 3.

Ланцюжок перевірки RTL:

```
tools/iqgen.py ──> sim_data/sim.iq (+ .json з очікуваними байтами)
                      │
       ┌──────────────┼──────────────────────────┐
       ▼              ▼                          ▼
tools/demod_model.py  tb_rtl_demod.sv     plot_rtl_demod.py → tb_fsk_demod_plot
(еталон на Python,    (RTL на sim.iq,      → rtl_plot.csv → rtl_demod_plots.html
 біт у біт як RTL)     порівняння з        (графіки всіх етапів — звідси ідея
                       sim.expect.txt)      екранів на дисплеї)
```

Відмінність від C-версії: `sim.iq` — GFSK на −1087 кГц, ±25 кГц, із синхрословом і CRC;
синтетика на платі — простіша (§7.1).

## 11. Чого ще немає і куди далі

* **SD-карта + FatFs (Блок 2)** — щоб грати справжні I/Q-файли замість синтетики. Пам'яті в 32 КБ
  для FatFs, найімовірніше, не вистачить — треба більша BRAM або зовнішня пам'ять.
* **RTL-демодулятор у Block Design** — тоді демодуляцію робитиме залізо, а MicroBlaze лише малює.
* **Синхрослово і CRC у C-декодері** — щоб пакет обрізався точно і перевірялась цілісність.
* **UART** на платі є, але в дизайн не підключений — `xil_printf` зараз нічого не друкує.
* **Автономний старт** — вшити ELF у бітстрім і записати у flash, щоб не треба було JTAG.

## 12. Словник

| Термін | Що це |
|---|---|
| I/Q | пара чисел на кожен момент: комплексний відлік сигналу після перенесення на «нуль» |
| Fs | частота дискретизації, відліків за секунду (тут 4.5 МГц) |
| FSK | частотна маніпуляція: 0 і 1 передаються різними частотами |
| NCO | цифровий генератор синуса; разом з множенням зсуває частоту |
| децимація | зменшення кількості відліків (тут /16) з фільтрацією |
| дискримінатор | обчислює миттєву частоту з фази сусідніх відліків |
| burst | пакет — шматок часу, коли передавач увімкнений |
| AFC | автопідстройка частоти — компенсує зсув несучої |
| слайсер | рішення «0 чи 1» за порогом |
| FFT, бін | швидке перетворення Фур'є; бін — одна «смужка» частот (тут 17.6 кГц) |
| dBFS | децибели відносно повної шкали АЦП (0 dBFS — максимум) |
| max hold | показувати максимум за час, а не середнє — для імпульсних сигналів |
| waterfall | спектр у часі: кожен рядок — спектр одного моменту, колір — рівень |
| BRAM, LMB | пам'ять у FPGA і шина до неї |
| AXI4-Lite | шина регістрів між процесором і периферією |
| JTAG, XSCT | інтерфейс відладки і інструмент Xilinx, яким заливаємо плату |
| ELF | файл зібраної програми |
| bitstream | файл конфігурації FPGA (опис заліза) |
| XSA | опис заліза для програмних інструментів (адреси, процесор) |
| LTO | оптимізація всієї програми разом на етапі лінкування |
